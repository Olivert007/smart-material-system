# 模块 04 · 治理 Copilot 与自学习

> 接口：`POST /api/govern/map-suggest`（依赖 LLM）、`POST /api/govern/confirm`（人工确认，只写 meta）。
> 标准字段枚举以本节 §1 为 SSOT（含事实表域列）；实现阶段同步 `STD_FIELDS`。
> 版本：Phase 2.2（2026-08-08）：冲突只进人工；业务库写入走 master_apply / rule_replay（00 §3.1）。
> 编排细化：字典 → **embed 召回** → fast 建议 → 低置信 escalate big；多候选仅预填（[09](09-多模型编排策略.md)）。

## 1. 标准字段枚举

映射目标分两层：**通用列**（跨表）+ **域列**（对齐 6 表 SCHEMA）。`std_field` 必须 ∈ 下表 ∪ `ignore`；表级目标由接入配置 `target_table` 指定（03 §1.1），字段映射不得发明枚举外名字。

### 1.1 通用 / 资产台账列

| 标准字段 | 含义 | 常见中文表头 |
|---|---|---|
| `asset_code` | 资产编码 | 资产编号、资产编码 |
| `material_code` | 物资编码 | 物资编号、物料编码 |
| `item_name` | 名称 | 名称、物资名称、资产名称 |
| `specification` | 规格型号 | 规格、型号、规格型号 |
| `quantity` | 数量 | 库存数量、数量、需求数量 |
| `unit` | 单位 | 单位、计量单位 |
| `location` | 存放地点 | 存放地点、库位、位置 |
| `department` | 部门 | 部门、所属部门 |
| `keeper_or_user` | 保管/领用人 | 保管人、使用人、领用人 |
| `status` | 状态 | 状态、资产状态 |
| `serial_or_factory_no` | 序列号/出厂编号 | 序列号、出厂编号、SN |
| `purchase_date` | 购买日期 | 购买日期、购置日期 |
| `remark` | 备注 | 备注、说明 |

### 1.2 事实表域列（对齐 02 六表）

| 标准字段 | 典型目标表 | 含义 | 常见中文表头 |
|---|---|---|---|
| `region` | fact_inventory 等 | 区域 | 区域、地区、仓库区域 |
| `category` | dim_material / 事实表 | 分类 | 分类、物资类别、品类 |
| `stock_qty` | fact_inventory | 库存数量（与 `quantity` 同义时可归一） | 现有库存、账面数量 |
| `stock_value` | fact_inventory | 库存金额 | 金额、库存金额、总价 |
| `flow_type` | fact_stock_flow | 出入类型 | 入库/出库、流向 |
| `flow_date` | fact_stock_flow | 流水日期 | 出入库日期、业务日期 |
| `flow_person` | fact_stock_flow | 经手人/领用人 | 领用人、经手人、使用人 |
| `flow_purpose` | fact_stock_flow | 用途/原因 | 用途、使用说明、去向 |
| `flow_in_text` / `flow_out_text` | （清洗中间态→fact_stock_flow） | 出入库自由文本列 | 入库记录、出库记录 |
| `demand_period` | fact_demand | 需求期次 | 期次、计划期、年度 |
| `quota_qty` | fact_quota_adjust | 定额/调整量 | 定额、调整数量 |

> `fact_stock_flow` 的文本拆解、置信分级、勾稽与自学习示例池见 **[12-出入库流水解析.md](12-出入库流水解析.md)**；本节仅登记标准字段名。

- 同义归一：表头映射到 `quantity` 或 `stock_qty` 均可，接入配置的 `columns[].std_field` 在写入前按 `target_table` 再投影到物理列（投影表维护在 meta，变更走 04 §6.7）。
- `ignore`：明确不入库列（如外部ID、纯备注列若业务不需要可 ignore）。

## 2. 处理流程

```
上传文件 → 提取表头列
  │
  ▼
① 规则字典优先匹配（四层：精确 → 归一化 → 同义词，命中直接采用，不耗 LLM；见 §6）
  │ 未命中 / 需候选
  ▼
①′ embed 召回标准字段 / 历史映射 Top-K（只排序预填，不自动发布）
  │
  ▼
② LLM 建议映射（默认 fast；低置信 escalate big；注入枚举 + 召回候选）
  │
  ▼
③ 返回 {"列名": "标准字段"} + 候选列表 + 未映射列清单
  │
  ▼
④ 治理中心人工确认（可修改/确认/忽略；多候选不可静默选）
  │
  ▼
⑤ 确认结果回写规则字典（自学习闭环，见 §6）
```

## 3. 实测结果（过渡：Qwen2.5-7B；目标 fast=9B）

输入 `["资产编号","名称","规格型号","数量","单位","存放地点","保管人","状态","备注","外部ID"]`：

```json
{
  "mapping": {
    "资产编号": "asset_code", "名称": "item_name", "规格型号": "specification",
    "数量": "quantity", "单位": "unit", "存放地点": "location",
    "保管人": "keeper_or_user", "状态": "status", "备注": "remark",
    "外部ID": "ignore"
  },
  "unmapped_columns": ["外部ID"]
}
```

10 列全部映射正确，`外部ID` 正确建议忽略。

## 4. 置信度分级

- **高置信**（表头与标准字段强匹配）：自动采用，进入管道。
- **低置信**（模糊/歧义，如"备注"可能不是备注）：进人工确认清单。
- 判定依据：LLM 可同时输出置信度；或按标准字段候选词命中数规则评分。

## 5. 人工确认接口

`POST /api/govern/confirm`

```json
{"source": "file_xxx", "detail": "表头'数量'→quantity", "decision": "accepted", "note": ""}
```

- `decision`：`accepted`（采用）/ `fixed`（改后采用）/ `ignored`（忽略）。
- 记录落库 `meta.sqlite.govern_confirm`，供回写与审计。

## 6. 自学习闭环

**落地决策（2026-08-06）**：四层匹配链路（精确→归一化→同义词→LLM）、冲突仲裁"次数优先+最新辅"、人工"忽略"记负例。

### 6.1 规则字典表 `rule_dict`（meta.sqlite）

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `header_raw` | 原始表头（如 `库位`） |
| `header_norm` | 归一化后表头（去空格、全角→半角、去括号注释、统一小写） |
| `std_field` | 目标标准字段；`ignore` 表示负例 |
| `hits` | 累计确认次数 |
| `last_source` | 最近来源文件（file_id） |
| `confirmed_by` | 确认人（审计） |
| `created_at` / `updated_at` | 时间戳 |

唯一键 `(header_norm, std_field)`；同义词映射单独维护 `synonym` 表（见 6.5）。

### 6.1.1 流水拆解示例池 `flow_example`（meta.sqlite）

与表头 `rule_dict` 并列的自学习资产，专用于出入库自由文本（详情 [12 §5](12-出入库流水解析.md)）：

| 列 | 说明 |
|---|---|
| `text_norm` | 归一化原文 |
| `flow_json` | 确认后的结构化拆解（可多段） |
| `level` | L1/L2/L3 或负例标记 |
| `hits` / `confirmed_by` / 时间戳 | 同 rule_dict 审计语义 |

冲突与负例原则同 §6.2 / §6.4；变更影响评估走 §6.7。

### 6.2 四层匹配链路（map-suggest 执行顺序）

```
① 精确命中    header_raw 与字典原样一致（含 ignore 负例）→ 直接采用/忽略
② 归一化命中  header_norm 一致（容忍空格、全角、括号注释、大小写差异）
③ 同义词命中  header 命中同义词表（如"库位"→"存放地点"）→ 映射到目标字段
④ LLM 建议    前三层未命中才调 LLM → 人工确认 → 回写字典
```

- **字典永远优先于 LLM**：字典是人工累积结果，LLM 建议只在字典未命中时生效。
- 负例（`std_field=ignore`）在①/②/③命中即直接建议忽略，**不再调 LLM**，避免重复打扰。
- 命中来源（exact/fuzzy/synonym/llm）随结果返回，前端可展示"命中字典"标签。

### 6.3 回写时机（govern/confirm 联动）

| decision | 回写动作 |
|---|---|
| `accepted` | 表头 → 确认字段，`hits+1` |
| `fixed` | 表头 → 修正后字段，`hits+1`（若已存在旧映射，按 6.4 仲裁） |
| `ignored` | 表头 → `ignore` 负例写入 |
| 回写同时记录 | `last_source`、`confirmed_by`（审计链） |

### 6.4 冲突处理（多候选不可自动发布）

```
同一作用域内 (header_norm) 有多个候选 std_field
  ├─ hits / updated_at 仅用于排序与 UI 预填
  └─ 只要存在 >1 个非 ignore 候选 → pending_conflict
     不得写入「可发布清洗配置」，须人工裁决后回写
```

- **作用域**：建议键增加 `business_domain` / `source_system`（及可选相邻列表征），避免「库位」跨场景误映射到错误标准字段。
- 单一候选且无冲突：可作为高置信预填，仍在治理中心可见可推翻。

### 6.5 同义词表

| header | 规范字段 | 类型 |
|---|---|---|
| 库位 / 位置 / 存放位置 | 存放地点 | synonym |
| 领用人 / 使用人 / 保管人 | 保管/领用人 | synonym |
| 出厂编号 / SN / 序列号 | 序列号/出厂编号 | synonym |

来源：人工确认时手动维护 + 字典累积（同一含义不同叫法确认 2 次以上可自动建议合并）。

### 6.6 收益与边界

- 高频表头（名称、数量、单位…）命中字典后**零模型开销**；LLM 只处理真正的新表头。
- 同一单位不同叫法随确认次数自动收敛；负例让 ignore 决定也收敛。
- 字典带来源文件与确认人，全链路可审计；可随时导出手动修正。
- 边界：字典是**建议**不是**终审**——命中结果仍展示在治理中心，人工可推翻，推翻即回写更新。

### 6.7 规则变更治理：dry-run / 冲突 / 历史 / 回滚 / 缓存失效（08-07 新增）

**问题**：规则字典（6.1）、同义词表（6.5）、清洗配置、指标字典（模块 08）都是人工确认累积的"资产"。**改错一条规则影响面可能很大**——一次误确认会改变所有后续文件的映射结果，必须可预演、可回滚、可追溯。

**五项能力**：

| 能力 | 说明 |
|---|---|
| dry-run 预演 | 规则变更先在**历史证据副本**上试跑，看影响到的文件数与映射变化，确认后才生效 |
| conflict detection | 新规则与现有规则冲突（同一表头两个 std_field、同义词成环、与指标口径矛盾）→ 标记 `pending_conflict` 进人工，**不静默覆盖** |
| history | 每次规则变更记录版本：变更人 / 时间 / 旧值 / 新值 / 影响范围 / 生效批次 |
| rollback | **血缘重建**（00 D6）：规则版本回退 + 按 release 撤销派生行并重跑；不做通用 reverse |
| cache invalidation | 规则变更后失效相关缓存：字典匹配缓存、few-shot 选择缓存、指标口径缓存、预聚合结果 |

**规则版本与回滚**：

```sql
rule_dict 增加版本字段：(header_norm, std_field, version, valid_from, valid_to)
```

- 变更 = 新版本生效（`valid_to=null`），旧版本 `closed`（`valid_to=变更时间`）——**不物理删除**，历史可查。
- 规则版本回退 = 旧版本重新 `active`；受影响确认标记可重审。
- **数据回滚**走 03 §4.8：按 `release_id` 撤销派生行 → 用指定配置版本重建，而非「逆操作」。
- 变更 dry-run 带出影响文件清单。

**dry-run 预演流程**：

```
规则变更（表头映射 / 同义词 / 清洗配置 / 指标口径）
  │
  ▼
① 在历史证据副本上试跑：命中该规则的（文件数, 列数, 映射变化 diff）
  │
  ▼
② 冲突检测：新规则 vs 现有规则 → 冲突清单
  │
  ▼
③ 影响评估报告（与 03 §4.5 staging 同一方法论，mutates_state=false）
  │
  ▼
④ 人工确认 → 生效（版本 +1）；或取消（无副作用）
```

**缓存失效（cache invalidation）**：
- 字典匹配结果、few-shot 池选择、指标口径注入、预聚合表——凡依赖被变更规则者，变更后一律失效重建。
- 统一由"规则版本表"驱动：读侧带版本号，版本变化即缓存 miss（与 03 §4.5 format fingerprint 同思路）。

**与 08 指标口径衔接**：指标定义改动（version+1，模块 08 §7）同样走本节 dry-run + 影响评估——先看会改变哪些历史查询结果，再确认生效。

## 7. 主数据治理闭环（新物料发现 / 冲突检测 / 审批 / 回写）

**问题**：主数据字典（`dim_material`，见 `master_data.py`）不是静态的——新文件接入不断产生**新物资编码 / 名称 / 规格**（03 §1.1 主数据三层匹配后仍匹配不上 → L3 独立物料）。若无治理，主数据会累积出同码异物、一物多码、重复物料，且无来源审计。

**核心原则**：与规则字典（§6）同一思路——**主数据也是"人工确认即资产"**，LLM/规则只负责候选与冲突发现，审批权在人工。

### 7.1 流程

```
03 Step5 主数据关联（三层匹配：L1 编码精确 / L2 名称+规格 / L3 独立）
  │ 匹配不上（L3）
  ▼
① L3 独立物料 → 进 master_pending 队列（自动入队，不阻塞接入流程）
  │
  ▼
② 冲突检测（规则，不耗 LLM，见 7.2）
  │
  ▼
③ 治理中心审批（7.3）：
   - 新物料  → 入主数据字典（编码/名称/规格/分类/单位）
   - 冲突    → 合并 / 改码 / 拒绝，结论回写
  │
  ▼
④ 回写：dim_material 新增或更新 + 事实表 material_id 重新关联（基于证据层与清洗配置重跑，03 §3.2 原则）
```

### 7.2 冲突检测规则

| 冲突类型 | 判据 | 处理 |
|---|---|---|
| `code_same_name_diff` 同码异物 | 编码相同、名称不同 | 人工定"改名 or 新物料"；改名则更新字典并重关联事实表 |
| `name_same_code_diff` 一物多码 | 名称+规格归一化后相同、编码不同 | 合并：保留主编码，其余编码并入，事实表重关联 |
| `spec_diff` 疑似新规格 | 名称相似（归一化相等或编辑距离 < 阈值）、规格不同 | 确认新规格 → 独立物料入字典 |
| `dup_pending` 重复提交 | 与 pending 现有候选相同 | 合并去重 pending 条目 |

- 判据全部在规则层计算（DuckDB / 字符串相似度），LLM 只做"疑似同物料候选"的解读建议。
- 首次接入历史文件时新物料可能大批涌入 → 提供**批量审批**模式：按编码/名称归组，一键批量确认（与 03 §1.2 `history_copy` 配合，历史副本默认跳过，避免历史物料污染主数据）。

### 7.3 `master_pending` 表（meta.sqlite）

| 列 | 说明 |
|---|---|
| `pending_id` | 主键 |
| `material_code` / `material_name` / `spec` | 候选物料（L3 独立） |
| `source_file` / `source_rows` | 来源文件与证据行（可定位到证据层） |
| `match_level` | 未匹配原因（L3 独立 / 匹配到 pending） |
| `conflict_type` | 冲突类型（7.2 枚举） |
| `candidates` | 疑似同物料候选（编码/名称/规格 JSON） |
| `status` | `pending` / `approved` / `merged` / `rejected` |
| `decided_by` / `decided_at` / `note` | 审批审计 |
| `created_at` | 时间戳 |

### 7.4 与自学习闭环（§6）衔接

- 审批结论回写 = 主数据版"规则字典"：`approved` → 入 `dim_material`；`merged` → 记录合并映射；`rejected` → 负例（同码异物判定结论存档），下次同编码/同名称出现直接建议，减少重复打扰。
- 合并/改码后事实表重关联可重跑：依赖"原始文件 + 确认配置"最小重跑集合（03 §3.2），可审计可复现。
- 与指标字典（模块 08）一致：**主数据定义权在人工**，LLM 只提候选，杜绝幻觉驱动主数据。

## 8. 边界与兜底

- LLM 未就绪：`map-suggest` 的**字典层（精确/归一化/同义词）照常工作**——命中的表头直接映射，不依赖 LLM；仅未命中的表头返回 `ok:false, llm:"unavailable"`，提示手写映射。
- 模型输出非 JSON / 解析失败：先走**容错解析层**（01 §5.5：去 JSON fence / 截取对象 / 值归一化），仍失败才返回空映射 + `fallback_reason`，提示重试或人工处理，不报错中断。
- 互验冲突：fast 与 big 不一致 → **只进人工**，禁止「以 big 为准」自动采纳（00 C4 / 09）。
- 字典冲突：同表头多候选按 6.4（hits → 时间 → pending_conflict），仍冲突进人工，不静默覆盖。
- 主数据/规则生效写业务库：仅经 `master_apply` / `rule_replay` → writer（00 §3.1）。
