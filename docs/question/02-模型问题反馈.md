## 一、问题背景

`/models` 三模型同时常驻时逼近 128GB 统一内存上限，触发内存告警。已由实测 OOM 印证：big(27B bf16, 76GiB) + embed(9.9GiB) 常驻后再起 fast 7B 直接 `Engine core initialization failed`（`stage2_fast_oom_20260808T140221Z.json`）；停 embed（`EMBED_FALLBACK_LEXICAL=1`）后才双常驻成功（`stage2_fast_ok_20260808T142828Z.json`，not_claimed 24h gate）。

## 四、解决方案（三层）

**第一层：FP8 权重（最大头，方案 D4 本来要求）**
- 27B-FP8 权重约 28–29GB（vs bf16 54GB），util 0.45 稳态约 35–40GB
- ⚠️ 27B 混合注意力 + vLLM 0.26 aarch64 需先实测（方案 01 §3.2 预警），失败可回退 bf16（`MODEL_DIR=/models/Qwen3.6-27B bash scripts/start_vllm_big27.sh`）

**第二层：不强制三模型常驻（符合 D8）**
- fast 仅评测/加固/互验时起，用完即关；`policy_router` 已支持 fast 不可用 degraded_up→big
- embed 按需 + `EMBED_FALLBACK_LEXICAL=1`（config 已有）兜底
- harden/eval 批处理错峰执行

**第三层：结构级（可选）**
- embed 迁 CPU 推理（fastembed/ONNX，几百 MB，方案 01 §1.2 支持"embed 可 CPU"）
- 日常主生成降为 9B（方案目标 fast=Qwen3.5-9B），27B 仅复杂 SQL/低置信修正/评测按需
- GGUF + llama.cpp 部分层 CPU offload（利用统一内存，牺牲延迟）
- 内存看门狗脚本（接近阈值先停 embed/fast）

### 7.1 fast/embed 按需起停（✅ 已实现 2026-08-09）

- 动作：按优先级停 embed → fast → 告警；**不停 big**（交互主路径）
