# 模块 09 · 多模型编排策略（细化）

> 来源交叉：[来源/AI图片OCR识别整理3.md](来源/AI图片OCR识别整理3.md)  
> 版本：Phase 2.2（2026-08-08）  
> 依赖：[00-总览](00-总览.md) D4/D5/D8、[01-本地模型部署与多模型编排](01-本地模型部署与多模型编排.md)  
> **不以「调用更多模型」为目标**；目标是合适任务用合适模型，且失败/冲突时不产生错误高置信结果。

---

## 1. 目标与非目标

### 1.1 目标

1. 简单、高频、低风险 → 小模型，降延迟与内存压力。  
2. 复杂、低置信、高风险 → 升级主模型。  
3. 规则 / 指标模板 / 历史资产能处理的 → **不调生成模型**。  
4. 生成结果必须过结构、权限与业务规则校验。  
5. 普通任务允许服务降级；**关键互验禁止用降级结果冒充独立模型**。  
6. 审计记录真实模型、制品 revision、prompt 版本、证据范围、降级原因。  
7. 双模型是否长期常驻由业务评测决定（00 D8）。

### 1.2 非目标

- 不让多模型对每请求固定轮流生成。  
- 不用模型投票代替业务校验或人工确认。  
- 第一阶段不同时常驻三个大生成模型。  
- 不把模型自报 `confidence` 直接当执行依据。

## 2. 推荐模型池

### 2.1 角色与制品（须固定 revision / SHA256 / 实测内存）

| 角色 | 推荐制品 | 主要职责 | 阶段 |
|---|---|---|---|
| **embed** | `Qwen3-Embedding-0.6B` 或 `BAAI/bge-m3` | 表头/指标/主数据/few-shot **候选召回** | Stage 1 起 |
| **fast** | `Qwen/Qwen3.5-9B` | 摘要、常规画像、普通映射、简单 SQL | Stage 2 起 |
| **big** | `Qwen/Qwen3.6-27B-FP8` | 复杂 SQL、低置信修正、质量解释、接入建议 | Stage 1 主生成 |

过渡：现有 `Qwen2.5-7B-Instruct` 仅作基线对照 / Stage 1 前 PoC，**不作为长期 fast 主选**。

### 2.2 SQL 专项候选（互斥定位）

`Qwen/Qwen3-Coder-30B-A3B-Instruct-FP8` 与 big 做 A/B（复杂 SQL 执行正确率）。初期**不与** 9B+27B 三大生成模型同时常驻。测试后只能三选一：

1. 替换 big；或  
2. SQL 批处理窗口按需切换；或  
3. 收益不足，不进生产池。

### 2.3 不推荐长期部署

| 模型 | 原因 |
|---|---|
| Qwen3-32B-BF16 | 旧代、内存高 |
| Qwen3.6-27B-BF16 | 可单测；双常驻优先官方 FP8 |
| GGUF-Q8_0 | llama.cpp 路线，不与 vLLM FP8 参数混用 |

制品字段同 01：仓库/目录、格式（BF16/FP8/…）、revision、SHA256、峰值/稳态内存、vLLM 与镜像版本。

## 3. 编排总体架构

```text
业务请求
   ↓
PolicyRouter（确定性规则，禁止 LLM 路由）
   ├─ 规则 / 指标模板直接处理
   ├─ Embedding 候选召回
   ├─ fast 生成 → 校验 → 低置信/失败 → big 修正
   └─ big 直接生成
   ↓
OutputValidator（Schema / SQL AST / 业务规则）
   ├─ 可执行（仍可能进 staging）
   └─ 待人工 / 拒绝
```

| 组件 | 职责 |
|---|---|
| **ModelRegistry** | 角色、端点、制品版本、能力、健康状态 |
| **TaskPolicy** | 每类任务 primary / escalate / 预算 / 超时 / risk |
| **PolicyRouter** | 按任务类型、复杂度、风险、健康选路径 |
| **ModelClient** | OpenAI 兼容调用、结构化输出、超时、审计 |
| **OutputValidator** | Pydantic/schema、SQL AST、标识符与动作白名单 |
| **ConfidenceScorer** | 规则命中、召回相似度、校验、历史通过率（综合分） |
| **EscalationEngine** | 是否 fast→big |
| **ConflictResolver** | 仅判定一致 / 冲突 / unverified；不自动选侧 |
| **CircuitBreaker** | 按模型与任务熔断 |

实现落点：`app/llm.py` 拆分为上述模块（或同文件分区）；路由表进 SQLite `task_policy` 可热更新（变更走 04 规则治理）。

## 4. 任务路由策略

### 4.1 TaskPolicy 表（SSOT）

```python
TASK_POLICY = {
    "summary":         {"primary": "fast", "escalate": "big", "risk": "low",    "max_calls": 2},
    "profile":         {"primary": "fast", "escalate": "big", "risk": "medium", "max_calls": 2},
    "map_headers":     {"primary": "fast", "escalate": "big", "risk": "medium", "max_calls": 2},
    "sql_simple":      {"primary": "fast", "escalate": "big", "risk": "medium", "max_calls": 2},
    "sql_complex":     {"primary": "big",  "escalate": None,  "risk": "high",   "max_calls": 2},
    "quality_explain": {"primary": "fast", "escalate": "big", "risk": "medium", "max_calls": 2},
    "ingest_plan":     {"primary": "big",  "escalate": None,  "risk": "high",   "max_calls": 1},
}
```

- `max_calls`：单次业务任务的**生成**调用上限（不含 embedding）。  
- 结构化解析失败：同模型最多修复 1 次；达预算 → 人工，禁止无限重试。

### 4.2 路由优先级（高 → 低）

```text
规则/模板命中
  > 历史确认资产
  > Embedding 唯一高相似候选（仅预填；风险任务仍须 confirm）
  > big（高风险直达）
  > fast（可升级）
  > 人工
```

- 模型**不能**覆盖明确人工确认规则。  
- Embedding 结果永不直接写业务库。

## 5. 分场景编排

### 5.1 表头映射（对接 04）

```text
表头 + sheet 上下文
  → 规则字典（精确/归一化/业务域）
  → Embedding Top-K 历史映射
       ├─ 唯一高相似 → 预填 + 来源标记
       └─ 否则 → fast 结构化建议
  → std_field 白名单
       ├─ 高综合置信 → staging 预填
       └─ 低置信/冲突 → big 完整修正 → staging + 人工
```

上下文必须含：表头、相邻表头、sheet 角色、样本值、业务域、Embedding 候选；**禁止只发孤立列名**。

### 5.2 Text2SQL（对接 02 / 08）

```text
问题 → 指标名/别名/历史问法
  ├─ 唯一指标 → 模板填参 → AST → 执行
  └─ 未命中 → 复杂度分类
        ├─ simple → fast
        └─ complex → big
     → AST + 白名单 → 只读 dry-run → 口径/数值校验
     → 失败则 fast 结果交 big 完整修正（计入 max_calls）
```

复杂度信号：JOIN/子查询/窗口/排名/占比/环比；≥2 业务表；时间粒度推断；多指标候选；历史通过率低；实体无法唯一映射 schema；用户要求审计级结果。

**模型一致 ≠ SQL 正确**；终判以 AST、执行、指标测试为准。

### 5.3 新文件接入（对接 03）

```text
规则解析 + Workbook/Sheet Profile + 全量统计
  → Embedding 匹配格式指纹 / 历史确认配置
       ├─ 高相似 → staging 对照复用（不直接发布）
       └─ 新格式 → fast 角色/表头/区域建议
            ├─ 校验通过 → staging
            ├─ 低置信 → big 完整修正
            └─ 多级表头/堆叠/drift → 直达 big
  → 配置 schema 校验 → staging → confirm → writer
```

模型只读样本与统计摘要；全量清洗/质量/发布由规则 + writer。

### 5.4 质量解释（对接 03 Step3）

DuckDB **全量算**确定性指标 → fast 普通说明；严重异常/多因/阻断发布 → big 解释与治理建议。  
模型**不得**改写 gate 数值结论。

## 6. 置信度与升级

### 6.1 综合置信度（勿直接用模型自报）

| 因子 | 初始权重 | 说明 |
|---|---|---|
| 规则命中质量 | 30% | |
| Embedding 相似度 | 20% | |
| Schema/白名单校验 | 20% | |
| 历史同类通过率 | 15% | |
| 上下文完整度 | 10% | |
| 模型自报置信度 | **5%** | 上限极低 |

权重用历史确认数据校准，不写死为永久业务常数。

### 6.2 升级条件（任一满足：fast → big）

1. 综合置信低于阈值  
2. schema / 枚举 / SQL AST 失败  
3. 多个同等级候选  
4. 多区域 / 多级表头 / schema drift  
5. 多表或复杂聚合 / 指标歧义  
6. 数值或质量异常  
7. 任务 `risk=high`  
8. 历史人工修正率超阈值  

### 6.3 big 的输入包

须同时包含：原始问题或证据摘要、fast 输出与校验错误、候选规则/指标、完整输出 schema、指令「输出完整修正版，非增量补丁」。

## 7. 级联、互验与降级

### 7.1 级联（唯一推荐）

```text
fast 草稿 → big 审查并输出完整最终稿 → OutputValidator
```

禁止「小模型最后重写大模型结果」。

### 7.2 独立互验（少量关键任务，Stage 3）

```text
fast（禁止 fallback） ──┐
                        ├─ 结构化比较 → consistent / conflict / unverified
big（禁止 fallback）  ──┘
```

- 任一不可用 → `unverified`  
- 结构非法 → `invalid`，不参与一致判定  
- 冲突 → 人工，不按模型大小选  
- 一致 → **仍须**确定性校验，不直接获执行权  
- 审计：真实 `model_id` / revision / endpoint  

### 7.3 普通任务降级

| 场景 | 处理 |
|---|---|
| big 摘要/解释不可用 | 可转 fast，`degraded_down` |
| fast 低风险不可用 | 可转 big，`degraded_up` |
| big 复杂 SQL 不可用 | fast 可出候选，强制 `needs_confirm=true` |
| big 接入决策不可用 | 规则 + 待人工，不自动发布 |
| 互验任一不可用 | `unverified`，禁止 fallback |

降级**不得**提升结果置信等级。

## 8. 状态与审计字段

### 8.1 实例状态

`loading → configured → ready → degraded → unreachable → circuit_open → stopping`

### 8.2 单次调用状态

`not_invoked | ok | degraded_up | degraded_down | timeout | transport_failed | output_invalid | policy_blocked | conflict | unverified | quota_exhausted`

### 8.3 `llm_call` 字段（SQLite）

| 字段 | 说明 |
|---|---|
| call_id / trace_id | 调用与业务链路 |
| task_type / mode | direct / cascade / verify / escalate |
| requested_role / actual_role | |
| model_id / model_revision / endpoint | 真实制品 |
| prompt_version | |
| evidence_digest | 所见证据摘要 |
| input_tokens / output_tokens / latency_ms | |
| status / fallback_reason | |
| schema_valid | |
| created_at | |

默认不存完整敏感 prompt；存脱敏摘要 + 内容哈希。回放原文进独立审计存储并设保留期。

## 9. 推理引擎

| 选择 | 说明 |
|---|---|
| **默认** | 标准 **vLLM**（OpenAI API、连续批处理、结构化输出、FP8 safetensors） |
| vLLM-Omni 镜像 | 可复用，但只当标准服务用；须单测 Qwen3.5/3.6、FP8、aarch64、guided JSON |
| 对照 | SGLang（前缀缓存）/ llama.cpp（极低并发 GGUF）/ TensorRT-LLM（模型固定后压榨） |

引擎对比用**同一业务评测集**，不只看 tokens/s。详见 [10-模型评测与验收](10-模型评测与验收.md)。

## 10. DGX Spark 资源预算（压测起点）

| 项 | 初始建议 |
|---|---|
| Embedding | 独立小服务或 CPU；约 1–2GB，以实测为准 |
| max-model-len | 8192 |
| max-num-seqs | 每生成实例从 1 起 |
| 生成并发 | 全局 2；fast/big 各 1 |
| 文件分析并发 | 1 |

验收六态内存：空载 / 单 big / fast+big 常驻 / 双模型同发 / 双发+百万行 / 24h。  

双常驻不可接受时优先：保留 big → Embedding CPU/按需 → fast 按需或取消；**不优先**靠降低主模型量化质量硬撑多模型。

## 12. PoC 运行拓扑锁定（GB10 / 当前硬件 · 2026-08-09）

> **拍板结论**：在未通过 [10 §4](10-模型评测与验收.md) 前，**不 claim**「Stage 2 生产双常驻」。日常 PoC 固定如下，避免在 big+embed vs fast+big 之间反复抽换。

| 角色 | PoC 状态 | 说明 |
|---|---|---|
| **big** | 常驻 `:8001`（`qwen3.6-27b`） | Phase B 主生成；Text2SQL / 复杂映射 / 升级终稿 |
| **fast** | 常驻 `:8000`（`qwen2.5-7b` **过渡**） | 流水 LLM 兜底、常规映射；**非**长期 9B 主选 |
| **embed** | **停**（`:8002` 不启） | 映射/召回走 **lexical fallback**（`EMBED_FALLBACK_LEXICAL=1`） |

### 12.1 为何这样拍

1. 实测：fast(7B)+big(27B)+embed **三件套同驻易 OOM**；停 embed 后 fast+big 可稳跑。  
2. Phase B 交付更依赖流水 LLM 兜底与问答生成，**优先保 fast+big**，召回用词法降级可接受。  
3. 文档理想 Stage 1（big+embed）与当前 PoC **不一致** —— 以本锁为准标「PoC 过渡态」，正式验收仍按 00/10。

### 12.2 变更条件（任一满足才改拓扑）

| 目标拓扑 | 前提 |
|---|---|
| 回到 **big + embed**（关 fast） | 流水 LLM 可改走 big / 按需启 fast；要补强主数据召回时 |
| 上 **fast(9B)+big** 并 claim 双常驻 | 通过 [10 §4](10-模型评测与验收.md)（含 24h 无 OOM） |
| 三件套同驻 | 内存六态实测证明可长期稳态；否则禁止 |

未满足上表前：**禁止**为「对齐 Stage 编号」而重启 embed 挤掉 fast，或宣称生产双常驻。
