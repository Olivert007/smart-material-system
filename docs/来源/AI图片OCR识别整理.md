## 1. 执行结论

方案的业务方向和主要控制原则成立，可以作为项目基础，但当前版本不宜直接整体编码或上线。建议状态为：

**有条件通过，先完成 P0 架构修订，再进入 MVP 实现。**  
（以上为评审当时结论；正式状态已更新为：P0/P1/P2 文档闭环 → 见 [`../00-总览.md`](../00-总览.md) 头部与 [`../06-运维手册.md`](../06-运维手册.md) §11。）

**值得保留的核心设计：**

1. 数据和模型全程本地运行，符合离线与数据不出机要求。
2. LLM 只生成建议、SQL 或声明式配置，不直接拥有执行权。
3. 新文件经过证据层、staging、dry-run 和人工 confirm 后才发布。
4. 原始文件、清洗配置、发布记录和人工确认结果形成追溯链。
5. 指标口径通过指标字典和模板约束，不让模型自由解释核心指标。
6. 识别使用抽样，质量检查和入库使用规则引擎处理全量数据。
7. 模型失败可降级，语义冲突不静默选择任一模型结果。

**进入实现前必须解决的四个问题：**

1. DuckDB 与 API/worker 多进程写入模型不匹配。
2. 发布、重试和任务抢占缺少原子状态迁移与幂等定义。
3. 双模型互验在模型降级时可能退化成同一个模型自我验证。
4. 模型权重格式、实际内存占用与 vLLM 启动参数尚未绑定。

## 2. 方案重新整理

### 2.1 系统目标

系统不是一个通用聊天机器人，而是**物资数据治理平台**。主要业务闭环为：

1. 接收 Excel、CSV、JSON 等新文件。
2. 保存原始文件并生成不丢信息的证据层。
3. 识别 sheet 角色、表头、数据区域和格式异常。
4. 将源字段映射到标准字段，执行确定性清洗和质量检查。
5. 通过 staging 展示影响范围，由人工确认后发布到标准业务库。
6. 基于标准业务库提供指标查询和自然语言问答。
7. 将人工修正沉淀为规则、指标、主数据和 few-shot 资产。

### 2.2 推荐逻辑分层

| 层 | 职责 | 推荐技术 |
|---|---|---|
| 展示层 | 问答、接入、治理、指标、模型和运维界面 | Vue3 + Element Plus |
| API 层 | 身份边界、参数校验、业务编排、查询服务 | FastAPI |
| 发布层 | 业务库唯一写入者、幂等发布、审计和对账 | 单一 writer service |
| 任务层 | 文件解析、画像、规则计算、LLM 调用 | 可恢复 worker |
| 元数据层 | 任务、规则、指标、审计、模型调用记录 | SQLite WAL；多用户版再考虑 PostgreSQL |
| 分析数据层 | 标准事实表、维表、只读分析 | DuckDB + Parquet |
| 文件层 | 原始上传、证据、staging、归档、备份 | 宿主机持久化目录 |
| 模型层 | 快任务和准任务推理 | 两个独立 vLLM 服务 |

### 2.3 推荐运行拓扑

```text
本机浏览器
   │
frontend:8080 ── api:8010 ── SQLite meta/task
                     │
              intake-worker ── Parquet evidence/staging
                     │
              writer service ── DuckDB business
                     │
              vllm-fast:8000 / vllm-big:8001
```

- 推荐用 Docker Compose 管理独立服务；所有镜像和依赖预先导入本机，运行时不访问网络。
- 分容器不会导致多套业务库；防止双写依赖的是**唯一 writer、只读挂载和幂等协议**，而不是把所有进程放进同一个容器。
- 如果第一阶段必须复用现有 `vllm-omni-dev` 单容器，可以作为 PoC，但必须补进程管理器，并明确该形态**不是最终生产拓扑**。

## 3. 交叉 Review 发现

### 3.1 P0：阻塞实现的问题

#### P0-1 DuckDB 多进程写入冲突

03 允许 worker 使用同进程线程或旁路进程，05 又允许各 API 写 meta.duckdb。如果 API 与 worker 是独立进程，它们会竞争同一个 DuckDB 写锁。

处理意见：

- DuckDB 只承担分析数据，不承担并发任务队列。
- 元数据和任务状态改用 SQLite WAL。
- 业务 DuckDB 由单一 writer service 写入，其余服务使用只读连接。
- 如果坚持 meta 也用 DuckDB，API 必须单进程、worker 必须是同进程线程，并通过单写队列串行提交；不建议作为长期方案。

#### P0-2 发布缺少幂等和崩溃恢复协议

当前发布同时修改业务库和元数据库，但没有定义跨库失败后的恢复方式。重复点击 confirm、HTTP 重试或进程崩溃可能产生重复事实行或缺失 manifest。

必须补充：

- `release_id` 在全链路唯一，事实表保存 `source_release_id`。
- `(source_file_hash, config_version, target_domain)` 建唯一约束。
- confirm 使用条件更新，只允许 `STAGED -> RELEASING` 一次成功。
- 业务写入使用 `release_id` 做 delete-and-replace 或 merge，重复执行结果相同。
- 启动时扫描 `RELEASING`，根据业务库实际行数自动完成或补偿。

#### P0-3 双模型互验存在错误降级

现有伪代码中，big 调用失败后会降级到 fast；互验再把该结果当成 27B 结果，可能形成"7B 与 7B 一致"的假互验。

处理意见：

- 普通生成允许 fallback，**互验禁止 fallback**。
- 互验记录真实模型 ID、模型 revision、端点和输出摘要。
- 任一模型不可用时状态为 `unverified`，不能标记 `consistent`。
- 级联改为 **7B 草稿 -> 27B 审查/最终稿 -> 规则校验**，不再让 7B 重写最终结果。

#### P0-4 模型制品没有固定

Qwen3.6-27B 官方基础权重是 BF16 且包含视觉模块，不能只依据"27B 参数"推导为约 27GB。文档中的 Q8_0、普通 safetensors 路径和 vLLM 命令目前混在一起。

处理意见：

- 主模型明确为一个具体制品（例如 `Qwen/Qwen3.6-27B-FP8`），固定 revision。
- 不把 GGUF Q8_0 的体积用于估算 vLLM safetensors 部署。
- 下载完成后记录文件清单、SHA256、磁盘体积、加载峰值和稳态内存。
- 在 GB10 上验证 vLLM 0.26.0、aarch64、FP8、混合注意力和结构化输出。

### 3.2 P1：上线前必须解决

#### P1-1 本地离线不等于接口天然安全

完全只在本机使用时，应将映射绑定到 127.0.0.1。如果需要局域网访问，则上传、查数、治理、指标修改和运维接口都需要登录或角色权限。**CORS 不能代替鉴权。**

建议定义两种部署模式：

| 模式 | 网络 | 最低控制 |
|---|---|---|
| 局域网模式 | 指定 LAN 地址或反向代理 | viewer/operator/admin 登录与审计 |
| 单机模式 | 仅 127.0.0.1 | 危险操作使用 ops token |

- `POST /api/govern/confirm`、`POST /api/metrics` 和文件删除等 meta 写操作不能匿名。
- `confirmed_by` 必须来自认证主体，不能由请求自由填写。

#### P1-2 SQL 防线应使用 AST，不应依赖字符串黑名单

黑名单和剥注释可以作为辅助，但不能作为主要判定。应使用 sqlglot 等解析器：

- 只允许一个 statement。
- 根节点只能是 SELECT 或受约束的 WITH SELECT。
- 禁止 ATTACH、COPY、PRAGMA、INSTALL、LOAD 和文件/网络 table function。
- 表、列、函数和 schema 均使用白名单。
- DuckDB 连接关闭 external access，并限制内存、线程、结果行数和执行时间。
- 普通用户不开放自由 `/api/query`，优先使用指标模板和受控问答。

#### P1-3 冲突策略文档不一致

04 规定同表头多候选必须人工处理，又按 hits 和更新时间自动选。建议统一为：

- 历史统计只用于排序和预填，**多候选不能直接成为可发布配置**。
- 加入业务域、来源系统和相邻列作为规则作用域，避免"库位"等字段跨场景误映射。

#### P1-4 指标示例本身存在口径错误

`INV_VALUE_TOTAL` 的文字说明"不含临时库"，SQL 只过滤了空值，并未排除临时库。指标定义必须同时保存**可执行测试**：固定输入数据、预期值、容差和适用版本。指标修改通过测试后才能激活。

#### P1-5 回滚不能简单理解为执行 reverse

主数据合并、事实表重关联、去重和规则重放通常不存在可靠的通用逆操作。推荐**按发布血缘重建**：保留原始文件、确认配置、release_id 和事实行来源；回滚时撤销目标 release 的派生行，再按指定规则版本重新生成。

#### P1-6 备份缺少一致性和恢复目标

CHECKPOINT 后直接复制文件不足以保证复制期间没有新写入。应暂停 writer 或使用受控快照，并将业务库、meta、原始文件、配置和 manifest 纳入同一备份批次。补充：

- RPO：建议 24 小时，关键发布前额外快照。
- RTO：先按 2 小时设计，以实际数据量验收。
- 每个备份生成清单和校验和。
- 至少每月执行一次恢复演练。

### 3.3 P2：建议优化

1. LLM 或 SQL 失败不宜全部返回 HTTP 200；可预期业务冲突用 409/422，依赖不可用用 503，便于监控。
2. 模型管理页不应在第一阶段支持任意下载、删除和动态 shell 重启；离线场景使用管理员预置模型清单更稳妥。
3. 原始文件"永久保留"需改为可配置保留策略，并考虑敏感数据、磁盘容量和删除审批。
4. 预聚合表应由确定性刷新任务维护，记录源数据版本，不能只在 prompt 中提示模型优先使用。
5. Text2SQL 的结果正确性不能主要依赖"双模型一致"；模型可能一致地生成错误 SQL，最终仍要靠指标模板、约束和测试集。

## 4. DGX Spark 模型部署意见

### 4.1 推荐实施顺序

- 第一阶段只部署已有 7B，验证完整数据闭环，不验证最终模型质量。
- 第二阶段部署 27B FP8，完成准确率和内存验收。
- 第三阶段才启用双模型常驻和互验。

不要在系统闭环尚未稳定时同时引入双模型、级联、互验、采样仲裁和动态切换，否则难以定位错误来自数据、规则、prompt 还是模型。

### 4.2 初始内存策略

128GB 是统一内存，模型、KV cache、操作系统、DuckDB、文件解析和 pagecache 共同使用。建议初始测试参数：

| 服务 | 初始建议 | 说明 |
|---|---|---|
| 7B | gpu-memory-utilization=0.25 | 先保证双实例和数据处理余量 |
| 27B FP8 | gpu-memory-utilization=0.45 | 需以实际权重加载结果校正 |
| 上下文 | ~max-model-len=8192 | 当前数据任务没有必要直接使用 262K |
| 文件分析并发 | 1 起步 | 大 Excel 解析和 DuckDB 统计也会占统一内存 |
| LLM 并发 | 每实例 1 起步 | 压测后再提升 |

0.25+0.45 只是保守起点，不是最终配置。验收时记录空闲、单模型、双模型、LLM 并发和百万行文件处理五种状态的内存峰值。

### 4.3 模型是否值得双常驻

双模型只有在固定评测集上显著优于单 27B 才值得保留。评测至少覆盖：

- 50 条简单查询。
- 30 份不同格式文件的表头和区域识别。
- 50 条多表、时间、排名和占比查询。
- 20 个故意包含口径歧义的问题。
- 20 个异常文件或错误 schema 场景。

比较准确率、人工介入率、首 token 延迟、总耗时、内存峰值和每任务调用次数。若双模型只带来很小收益，应改为 **27B 主模型 + 规则校验**，7B 仅用于摘要或在 27B 离线时降级。

## 5. 离线部署补充要求

离线交付包应包含：

1. 容器镜像 tar 包及 SHA256。
2. 两个模型的完整权重、tokenizer、config、revision 和 SHA256 清单。
3. Python wheelhouse、npm 离线依赖或已构建的前端产物。
4. Docker Compose、环境变量模板和启动/停止脚本。
5. 数据库初始化与迁移脚本。
6. 演示数据、固定评测集和验收脚本。
7. 备份恢复脚本和恢复演练说明。
8. 软件许可证、模型许可证和第三方依赖清单。

运行时应设置**离线模式**，禁止自动下载模型、pip/npm 依赖和远程 telemetry。模型管理页的"下载"改成"导入本地离线模型包"。

## 6. 分期实施建议

### Phase A：基础可信链路

- 确定标准 6 表、主键、来源列和指标样例。
- 建立 SQLite meta/task 和单 DuckDB writer。
- 实现文件落盘、哈希、证据 Parquet、任务恢复和幂等发布。
- 完成只读查询、AST 校验、备份恢复。
- 暂不引入 27B、双模型和复杂前端。
- **退出条件**：同一文件重复上传、重复 confirm、进程中途终止均不会重复入库或丢失审计。

### Phase B：单模型智能能力

- 接入 7B 或 27B 单模型。
- 实现结构化输出、schema 校验、prompt 版本和调用审计。
- 实现表头建议、Text2SQL 和规则降级。
- 建立固定评测集和人工修正流程。
- **退出条件**：核心查询准确率、字段映射准确率和人工介入率达到业务阈值。

### Phase C：27B 与双模型评估

- 部署固定的 27B FP8 制品。
- 完成 GB10 内存、并发、超时和长时间稳定性测试。
- 对比单 27B、7B+27B 级联和独立互验。
- 只保留有量化收益的编排模式。
- **退出条件**：连续运行 24 小时无 OOM，模型异常不会产生错误高置信结果。

### Phase D：治理和产品化

- 完成指标字典、规则版本、主数据审批和按血缘重建式回滚。
- 完成 8 个页面、运维告警和离线模型导入。
- 加入局域网模式所需的身份和权限体系。
- **退出条件**：完成一次全量备份恢复、规则回滚、模型故障降级和异常文件演练。

## 7. 最终验收门槛

### 数据正确性

- 任意事实行可追溯到原始文件、sheet、行列、配置版本和 release_id。
- 重复请求不会重复入库。
- 指标 SQL 有固定测试数据和期望结果。
- 主数据合并和规则回滚可通过血缘重建恢复。

### 模型质量

- Text2SQL 按执行正确率评估，不只检查语法合法率。
- 字段映射按字段级 precision/recall 评估。
- 双模型降级不会产生伪互验。
- 非法结构化输出不会进入规则执行器。

### DGX Spark 运行

- 双模型和百万行文件处理峰值不触发 OOM。
- 连续运行 24 小时无任务锁死和数据库写冲突。
- 容器或服务重启后任务自动恢复。
- 断网状态下能够完整安装、启动、运行和恢复。

### 运维安全

- 单机模式只绑定回环地址；局域网模式有登录和权限。
- 所有写操作、模型切换和规则回滚均有真实操作者审计。
- 备份校验和正确，恢复演练达到约定 RPO/RTO。

## 8. 建议确认的架构决策

在回写 00 至 08 前，需要明确以下决策：

| ID | 建议决策 |
|---|---|
| D1 | meta/task 使用 SQLite WAL，业务分析继续使用 DuckDB |
| D2 | 业务 DuckDB 采用唯一 writer service，所有发布必须幂等 |
| D3 | 最终服务使用 Compose 分容器；现有单容器只作 PoC |
| D4 | 主模型固定为明确的 FP8 制品和 revision，不再使用模糊的 Q8 表述 |
| D5 | 互验禁止 fallback；级联最终结果由 27B 输出、规则校验 |
| D6 | 回滚采用 release 血缘撤销与重建，不实现通用 reverse 操作 |
| D7 | 第一阶段只支持本机回环访问；需要 LAN 时再启用用户权限 |
| D8 | 双模型是否常驻由固定评测集结果决定，不作为预设硬约束 |

确认这些决策后，应统一修改 00 的硬约束、01 的模型与编排、03 的任务和发布、05 的鉴权与连接管理、06 的部署与恢复，避免继续保留两套互相冲突的描述。
