# 模块 03 · 新文件接入编排

> 场景：**进来一个新的 Excel**（格式可能与既有 8 个文件完全不同，文件可能很大）。
> 目标：不要求用户先整理表格，系统用不同本地模型分工编排，自动完成"识别 → 治理建议 → 接入决策"，人工只需确认。
>
> 版本：Phase 2.2（2026-08-08）  
> **落地决策（2026-08-06 / 修订 08-08）**：
> - 解析引擎：xls/xlsb/xlsm/ods 统一用 **calamine**；xlsx 大表保留 openpyxl read_only 流式。
> - 结构检测：**规则优先 + LLM 辅助**。
> - 大文件/批量：**可恢复任务队列**（`intake_task` + `intake_worker`，禁止仅依赖 BackgroundTasks，见 §3.1 / C9）。
> - 准模型统一 **big = 27B-FP8**（不再写 32B 主路径）；轻任务 Stage 2+ 走 **fast(9B)**，过渡可用 7B。
> - 表头/主数据候选：**embed 召回** + 字典优先（[09](09-多模型编排策略.md) / [04](04-治理Copilot与自学习.md)）。
> - 入库唯一经 staging confirm → `intake_release`（C5）；不走 `/api/ingest`。
> - 图片/PDF：PaddleOCR PP-Structure（待验证）+ rapidocr 兜底。
> - 先画像后识别：workbook/sheet profile 两段式（§1.2）。

---

## 1. 六步流水线（按任务轻重分配模型）

```
新 Excel 上传
 │
 ├─ Step0  规则解析 → 原始证据 parquet（无 LLM，已实现）
 ├─ Step1  文件画像        → 规则 + fast（轻；Stage 1 可 big/纯规则）
 │          ① Workbook Profile（纯规则）：枚举全部 sheet，角色初判/表头行候选/数据区边界/异常标记
 │          ② Sheet Profile（LLM 只处理存疑 sheet）：确认角色/表头/数据区/区域划分
 │          → 产出 workbook_profile / sheet_profile / structure / adapter / header_row（§1.1/§1.2 配置）
 ├─ Step2  表头映射        → 字典 → embed 召回 → fast（低置信 escalate big）
 │          表头 → 标准字段 + 清洗动作
 │          → 产出 columns[]（std_field / clean）；多候选仅预填；低置信进治理中心
 ├─ Step3  数据质量预检    → big（重）
 │          主键重复/缺失、必填字段缺失、数量单位异常、汇总明细不一致
 │          （规则引擎全量算，LLM 只解读结果）
 │          → 补充 dedup / 必填校验配置
 ├─ Step4  接入建议        → big（重；Stage 3 可互验）
 │          进哪张表（新事实表/并入现有/仅参考）？关联键建议？
 │          → 产出清洗配置草案（master / 目标表），见 §1.1
 ├─ Step5  执行清洗入库    → 规则引擎按确认后的配置执行（无 LLM）
 └─ Step6  入库核对        → fast（轻）
           新入库行数 vs 源文件 → 差异解读
```

### 1.1 配置驱动清洗：LLM 产配置，规则引擎执行

新文件的表结构、列名、语义都不确定，**清洗逻辑不能为每个文件写死 Python**（既有 8 文件是逐文件硬编码：sheet 名、表头行号、数量列清单、关联键列）。方案把清洗拆成两层：

**① 通用清洗原语**（与文件无关，已验证可复用）

| 原语 | 功能 |
|---|---|
| `norm` | 全角转半角 + 去空格 |
| `to_num` / `split_num_unit` | 提取数字 / 拆分"50米"→50+米 |
| `clean_date` | 多格式日期 → yyyy-mm-dd |
| `drop_allna` / `dedup` / `is_example_row` | 空行删除 / 去重 / 示例行识别 |
| 颜色标记提取 | 6 色语义（建设期/变更/删除候选…） |
| 错列检测 | 关键词参数化（室/层/楼/库…） |
| 主数据三层匹配 | L1 编码精确 / L2 名称+规格 / L3 独立物料 |
| `split_flow_text` | 出入库自由文本按分隔符拆多笔（见 [12](12-出入库流水解析.md) §4.1） |
| `extract_flow_fields` | 单段提取日期/数量/单位/经手人/用途 + 置信分级（[12](12-出入库流水解析.md) §4.2–4.5） |

这些是"清洗动作库"，验证过的逻辑，新文件无需重写。

> **流水拆解边界（12 FL2）**：上述两条原语仅在 **Step5 规则引擎**执行；对规则失败/低置信样本的 **LLM 兜底是独立 worker 任务**，不并入 Step5，产出进 `flow_pending` 须人工确认后才可发布（C3/C5）。

**② 每文件清洗配置**（LLM 编排生成 + 人工确认，落库可追溯）

```json
{
  "source": "新文件.xlsx", "sheet": "库存明细",
  "structure": "标准纵向", "adapter": "none", "header_row": 2,
  "columns": [
    {"header": "物资编码", "std_field": "material_code", "clean": "code"},
    {"header": "库存数量", "std_field": "quantity", "clean": "num_unit"},
    {"header": "入库日期", "std_field": "purchase_date", "clean": "date"},
    {"header": "入库记录", "std_field": "flow_in_text", "clean": "flow_text"},
    {"header": "出库记录", "std_field": "flow_out_text", "clean": "flow_text"}
  ],
  "master": {"code": "物资编码", "name": "物资名称", "spec": "规格型号"},
  "dedup": ["物资编码"],
  "flow_config": {
    "flow_columns": [
      {"header": "入库记录", "flow_type": "IN", "qty_column": "入库数量"},
      {"header": "出库记录", "flow_type": "OUT", "qty_column": "出库数量"}
    ]
  }
}
```

`flow_config` 细节与数量优先级见 [12](12-出入库流水解析.md) §3.1 / §4.5；无出入库文本列的文件可省略该块。

各步骤产出配置字段：

| 步骤 | LLM 产出 | 配置字段 |
|---|---|---|
| Step1 画像(fast) | 结构类型、表头行 | `structure` / `adapter` / `header_row` |
| Step2 表头映射(字典+embed+fast) | 列 → 标准字段 + 清洗动作 | `columns[].std_field` / `columns[].clean` |
| Step3 质量预检(big) | 规则全量算 + LLM 解读问题 | 补充 `dedup` / 必填校验 |
| Step4 接入建议(big) | 目标表、关联键 | `master` / 目标事实表 |
| Step5 执行（无 LLM） | 规则引擎消费以上配置清洗+关联+入库；含 `split_flow_text`/`extract_flow_fields`（[12](12-出入库流水解析.md)） | 全部 |
| Step5′ 流水 LLM 兜底（可选，非本步） | 仅 `flow_pending`；fast/big 建议 → 人工确认（[12](12-出入库流水解析.md) §3） | 有出入库文本且规则未覆盖 |
| Step6 核对(fast) | 入库行数 vs 源文件差异解读 | - |

配置经人工确认后落库（`intake_report`）；**修正即回写**，与模块 04 规则字典同一自学习思路——新文件第一次要人确认，确认过的配置下次直接复用，越用越不依赖 LLM。

**③ 区域级配置（schema drift / 多区域堆叠，08-07 新增）**

同一 sheet 内不同区域列含义可能漂移（列名相同含义不同，或列名都不同）——清洗配置从 sheet 级降为 **region 级**：区域切分（§2.2 `split_region`）后，每个子区域独立产出表头行与字段映射，规则引擎按 region 起止行号执行：

```json
{
  "source": "外部导出.xlsx", "sheet": "Sheet1",
  "structure": "多区域堆叠", "adapter": "split_region",
  "regions": [
    {
      "name": "区域A-库存", "start_row": 3, "end_row": 120, "header_row": 3,
      "columns": [
        {"header": "编码", "std_field": "material_code", "clean": "code"},
        {"header": "数量", "std_field": "quantity", "clean": "num_unit"}
      ]
    },
    {
      "name": "区域B-需求", "start_row": 125, "end_row": 300, "header_row": 125,
      "columns": [
        {"header": "编码", "std_field": "material_code", "clean": "code"},
        {"header": "需求数", "std_field": "quantity", "clean": "num_unit"}
      ]
    }
  ]
}
```

- **同名列含义漂移 = 各区域独立映射**：`编码`在区域 A 是物资编码、区域 B 是设备编码，各自映射到不同标准字段。
- LLM 只负责**确认区域划分与各区域角色**（§1.2 画像），数据转换全部由规则引擎按 region 边界执行，保证确定性与可审计。
- 配置校验（模块 05 §1）同步校验 region 边界合法（`start_row ≤ header_row ≤ end_row`、边界不重叠、columns 引用本区域 header）。

**为什么配置驱动而非 LLM 写代码：**
- **安全**：LLM 生成代码执行 = 任意代码执行风险（见模块 05）
- **可审计可重跑**：配置落库可追溯"为什么这么洗"，结果确定可重跑
- **改动最小**：新文件只换配置，通用原语零改动；原语有 bug 只改一处
- **兜底干净**：LLM 产出再离谱也只是配置错 → 人工改配置重跑，不碰代码

### 1.2 Workbook / Sheet Profile：先画像，后识别

真实输入是**内部异构、多 sheet、多格式的 Excel 集合**（资产汇总表、问题/处置/需求类汇总、库存台账、需求计划、参考目录、极宽外部导出…可能混在同一文件），不能假设"第一个 sheet 是明细""第一行是表头""每个 Excel 是一个标准表"。**任何识别之前必须先建立整体画像**，再逐 sheet、逐区域识别。

**第一段：Workbook Profile（纯规则，无 LLM）**

规则引擎枚举全部 sheet，产出 `sheet_profile` 清单（每 sheet 一条），全部在证据层上用 DuckDB 计算：

| 字段 | 内容 |
|---|---|
| `sheet` | sheet 名 |
| `rows` / `cols` | 行数 / 有效列数 |
| `density` | 非空密度（空行/空列比例） |
| `role_hint` | 角色初判（见下表） |
| `header_row_candidates` | 表头行候选（首 N 行文本密度高者） |
| `data_bounds` | 数据区起止行号 |
| `anomalies` | 异常标记：公式区 / 合并单元格区 / 隐藏列 / 颜色标记 / 分隔行 |

**sheet 角色枚举与判定规则**（规则可算，命中即初判，多命中取置信度高者）：

| 角色 | 判定信号 | 处理策略 |
|---|---|---|
| `detail` 明细 | 有表头行 + 数据行数多 + 无明显"合计/汇总"关键词 | 走字段映射入库 |
| `summary` 汇总 | 含"合计/总计/汇总/小计"关键词行；或首列为汇总维度（部门/区域/类别）且数值列多为聚合值 | 与明细做一致性校验（Step3）；可独立入库（若为独立汇总事实）或仅参考 |
| `reference` 参考/目录 | 无表头特征、列少、多为文本；sheet 名含"参考/目录/清单说明" | `report_only`，仅证据（§2.2） |
| `wide_export` 极宽导出 | 有效列数 > 阈值（如 60） | 列级抽样 + 分块映射（§2.4） |
| `history_copy` 历史副本 | sheet 名含"历史/旧/备份/副本"或日期后缀 | 默认跳过，仅证据 |
| `empty` | 非空密度 < 阈值 | 跳过 |
| `unknown` | 规则无法判定 | 交 LLM 画像 + 人工确认 |

**第二段：Sheet Profile（LLM 辅助，只处理存疑）**

- 规则判定明确（`detail`/`summary`/`reference`…）→ 直接进入 Step2，不调 LLM。
- 规则判定 `unknown`，或检出"区域堆叠 / schema drift / 多级表头 / 极宽"迹象 → 调 fast（或 Stage 1 的 big）画像确认：sheet 角色、表头行、区域划分、有无颜色标记；低置信进治理中心人工确认。
- 画像结论（角色、置信度、命中的规则与行号）落库 `intake_report`，可追溯。

**收益**：角色判定与表头识别解耦——先知道"哪些 sheet 是明细、哪些是汇总、哪些是参考"，Step2 字段映射才不会拿汇总表/参考目录去当明细洗。

**与 02 表画像衔接**：sheet profile 是"接入前"画像（来源证据层）；入库后业务库再生成表/字段画像（模块 02 §6.2）。二者同源——同一套"画像优先"方法论：**先看全貌，再让 LLM 解读**。接入时 sheet 角色结论可复用到入库后的表画像生成。

## 2. 格式适配框架（应对"格式不一样"）

**第一道保险是证据层**：任何文件先存成 `(sheet, row, col, raw_value)`，不假设结构。
**第二道是结构检测 + 适配器**：

```
未知文件 → 结构检测（规则优先 + LLM 辅助，见 §2.1）
   ├─ 标准纵向表     → 直接走管道
   ├─ 横向布局       → 转置适配器（表头在左列）
   ├─ 多级表头/合并  → 表头重建适配器（多行表头拼接为单行）
   ├─ 堆叠区域       → 区域切分适配器
   ├─ 稀疏大表       → 流式解析 + 抽样（已有 365 万单元格验证）
   └─ 纯报表式       → 仅证据，不抽取为明细
```

适配器选择由 **规则/LLM 建议 + 人工确认**（治理中心）；选错了不丢数——原始证据仍在，可重选重跑。
**适配器不改变证据层约定**：转换结果落为带 `adapter` 标记的新证据文件（如 `transpose:1`），后续步骤无感知。

### 2.1 结构检测（规则优先 + LLM 辅助）

判 sheet 是否"标准纵向"用规则先筛，**拿不准才调 LLM 画像**，控制模型开销：

| 规则（DuckDB/证据层直接算） | 判据 |
|---|---|
| 表头行密度 | 首 N 行中非空单元格占比高且多为文本 → 像表头 |
| 列方向扩展度 | 有效列数多（>3）且首行多为文本 → 纵向表 |
| 行方向扩展度 | 首列多为文本且列数少 → 疑似横向布局 |
| 合并/多级表头迹象 | 前几行行首文本重复（"2023年""Q1"），或表头行出现 NaN 后下行继续有值 → 多级表头 |
| 区域堆叠迹象 | 中部出现整行几乎为空的"分隔行"，分隔行两侧都有独立表头特征 → 堆叠区域 |

规则判定为"明确"→ 直接选适配器；"存疑"→ 走 LLM 画像（fast）给出 `structure_type` + 置信度，低置信进治理中心人工选择。
结构检测结果（类型、置信度、依据规则命中的行号）落库 `intake_report`，可追溯。

### 2.2 适配器转换规则（不丢数据）

| 适配器 | 输入 | 转换 | 产物标记 |
|---|---|---|---|
| 标准（无） | 原始证据 | 原样 | `adapter: none` |
| 转置 | 横向布局证据 | `(sheet,row,col,val)` → 左列字段名作新表头，顶部行为记录键 | `adapter: transpose` |
| 表头重建 | 多级表头证据 | 多行表头按列对齐拼接为单行（如 `2023年\|Q1\|数量` → `2023年Q1数量`），下移数据区起始行 | `adapter: rebuild_header` |
| 区域切分 | 堆叠区域证据 | 按分隔行切成 N 个独立子表，每个子表各自走标准/转置流程 | `adapter: split_region` |
| 纯报表 | 报表式证据 | 不抽取为明细，仅作参考证据 | `adapter: report_only` |

任何适配器只产出"标准化视图"，**原始证据 parquet 永不覆盖**；重选适配器 = 从原始证据重新转换，可重跑。

### 2.3 解析引擎选型

| 格式 | 引擎 | 说明 |
|---|---|---|
| xlsx | openpyxl `read_only` 流式 | 已验证 365 万格；稀疏大表只抽证据 |
| xls / xlsb / xlsm / ods | **calamine**（pandas `read_excel(engine="calamine")`） | 一个库全覆盖；`_SUPPORTED` 扩展，治理层无感知 |
| csv / json | 现有 pandas / json | 不变 |
| PDF / 图片 | **PaddleOCR PP-Structure**（主）+ rapidocr（兜底） | 表格图 → 单元格文本+行列位置 → 还原为证据四元组（`sheet="pdf"`）；aarch64 安装与推理性能**待小样本验证**后再启用 |

> calamine 全量加载：对超阈值大文件需先抽样（`nrows` 截断头部），中部/尾部采样用分片读取或直接以证据层标记"基于抽样"——与 §3 区域采样策略配套。

### 2.4 单元格级异常处理（公式 / 隐藏列 / 合并 / 极宽）

真实表格的"格子"不是规整值：有公式、有隐藏列、有合并单元格、有超宽列。策略是**证据层全保留，识别/入库层显式决策**：

| 异常 | 处理策略 |
|---|---|
| 公式单元格 | openpyxl 同时读**公式串与缓存计算值**（`data_only`）；证据层双存 `raw_value`（计算值）+ `formula`（公式串）；识别/入库用计算值；无缓存值（未计算保存）标 None 并提示"可疑列"；含公式的区域判为**动态汇总**，不入明细（§1.2 `summary`） |
| 隐藏列 | 证据层保留 `hidden` 标记；默认**不把隐藏列当数据列**喂表头映射；放入"辅助列池"（隐藏列常含状态码/内部编码等主数据匹配线索，供主数据三层匹配使用）；配置可显式 `include_hidden: true` 恢复为数据列 |
| 数据区合并单元格 | `merged_cells` 定位；数据区合并 → **前向填充**（down-fill）为标准值；证据层保留"仅首格有值"的原始状态，审计可还原 |
| 极宽表（列方向超宽） | 列数 > 60 触发：表头映射**分块**喂（每块 ≤ 20 列）；**列重要性规则**（列名含 编码/名称/数量/单位/金额/日期 等词者优先，先列取舍再入库）；全量列仍留证据层，不丢 |

> 与 §3 区域采样配套：§3 解决"行方向超长"，§2.4 解决"列方向超宽"，二者可叠加。

### 覆盖矩阵

| 格式差异 | 覆盖 | 机制 |
|---|---|---|
| 扩展名不同（xlsx/csv/json） | ✅ 已实现 | 统一证据层 |
| 表头位置不固定 | ✅ | Sheet Profile 定位 header_row（§1.2） |
| 表头叫法不同 | ✅ 已实现 | LLM 表头映射 |
| 多 sheet 角色混排（明细/汇总/参考/目录/极宽/历史副本） | ✅ 方案已定 | Workbook Profile 角色判定（§1.2），每 sheet 独立画像 |
| 汇总表（资产/问题/处置/需求类） | ✅ 方案已定 | `summary` 角色：与明细一致性校验 / 独立入库 / 仅参考（§1.2） |
| schema drift（不同区域列含义变化） | ✅ 方案已定 | 区域级配置 `regions[]`（§1.1 ③）+ 区域切分适配器（§2.2） |
| 合计行/说明行/隐藏行 | ✅ | 识别为证据，不当明细 |
| 颜色标记 | ✅ 已实现 | 6 色语义（建设期/删除候选/变更…） |
| 稀疏大表/宽表（行方向超长） | ✅ 已实现 | 流式 + 抽样证据（§3） |
| 极宽表（列方向超宽） | ✅ 方案已定 | 列分块映射 + 重要性规则（§2.4），未实现 |
| 公式单元格 | ✅ 方案已定 | 公式串 + 缓存值双存；含公式区域判动态汇总（§2.4） |
| 隐藏列 | ✅ 方案已定 | 证据带 hidden 标记；默认不进数据列，入辅助列池（§2.4） |
| 数据区合并单元格 | ✅ 方案已定 | merged_cells 定位 → 前向填充（§2.4） |
| 横向布局 | ✅ 方案已定 | 转置适配器（§2.2），结构检测规则优先 |
| 多级表头/合并表头 | ✅ 方案已定 | 表头重建适配器（§2.2），多行表头拼接为单行 |
| xls/xlsb/xlsm/ods | ✅ 方案已定 | calamine 统一引擎（§2.3），未实现 |
| PDF/图片表格 | ⚠️ 待验证 | PaddleOCR PP-Structure 表格还原 + rapidocr 兜底（§2.3） |
| 纯报表式 Excel | ✅ 降级处理 | 仅参考证据，不入库 |

## 3. 大文件覆盖策略（文件可能很大）

**核心原则：识别用样本，入库用全量。LLM 只碰小样本，重活全在 DuckDB/规则侧。**

| 环节 | 策略 | 现状 |
|---|---|---|
| 画像/识别 | 只喂抽样：表头附近 + 数据中部 + 尾部各取样本，标注"基于抽样" | ✅ 方案已定：区域采样（头/中/尾各 N 行），替代现有"前 5000 行一刀切" |
| 表头映射 | 只喂表头行（十几列），与文件大小无关 | ✅ |
| 质量预检 | 规则引擎全量算（DuckDB 级），LLM 只解读统计结果 | ✅ 方案已定：27B 解读；解读 prompt 未落地 |
| 入库 | 全量流式进 DuckDB，不走 LLM（CSV/Parquet COPY / chunk 写库） | ✅ 方案已定：COPY 直插为主；百万行需构造测试数据验证 |
| 上传接口 | 大文件异步：立即 202 + task_id，轮询进度 | ✅ 方案已定：`intake_task` 表 + `intake_worker`（§3.1，禁止仅 BackgroundTasks） |
| 批量文件 | 任务队列逐个处理，单个失败挂"待治理"，不阻塞整体 | ✅ 方案已定：`intake_task` 队列 + 启动回收孤儿（§3.1） |

**已验证**：365 万幽灵单元格的稀疏大表，openpyxl read_only 流式解析正常跑完。

### 3.1 异步任务与批量队列（`intake_task`，可恢复）

**上传不再同步等解析完成**：`POST /api/files` 立即返回 `task_id`（HTTP 202），文件落盘后入队；前端轮询/SSE 进度。  
限额与压缩炸弹见 [05 §1.4](05-安全与API规范.md)（原始单文件默认 2GiB；解压膨胀默认 500MiB）。鉴权：上传入队为过程性 meta 写（单机可无 ops）；**confirm 发布**须 ops（05 §1.5）。

**约束 C9**：不得把唯一执行载体绑在 FastAPI `BackgroundTasks` 上（进程退出即丢）。规范实现：

| 组件 | 职责 |
|---|---|
| `intake_task` 表 | 任务状态 SSOT；worker 只认表，不认内存队列 |
| `intake_worker` | 独立循环（同进程线程或旁路进程均可）：抢占 `pending` → `processing` → 终态 |
| 启动回收 | API/worker 启动时：将超时未心跳的 `processing` 置回 `pending`（或 `failed` 可重试），避免僵尸卡死 |
| 心跳 | `processing` 每 N 秒更新 `heartbeat_at`；超过阈值（如 30 分钟）触发 06 §8 卡死告警 |

`meta.sqlite` 表 `intake_task`：

| 列 | 说明 |
|---|---|
| `task_id` | 主键（uuid 短码） |
| `file_id` | 关联 file_batch |
| `filename` | 原文件名 |
| `task_type` | `parse_evidence` / `analyze` / `batch` |
| `status` | `pending` → `processing` → `done` / `failed` / `pending_govern` |
| `progress` | 0~100 |
| `message` | 状态说明/错误信息 |
| `adapter` | 结构检测选定的适配器（§2.2） |
| `heartbeat_at` | worker 心跳 |
| `attempt` | 重试次数（上限可配，如 3） |
| `created_at` / `finished_at` | 时间戳 |

**流程**：

```
POST /api/files（或 /api/files/batch）
  │ ① 落盘 + INSERT intake_task(pending) + 返回 task_id（202）
  ▼
intake_worker：结构检测 → 适配器 → 证据 parquet → 更新状态
  │ ② 轮询 GET /api/tasks/{task_id}
  ▼
done：进入画像/映射/质量/建议 → staging → 人工 confirm → intake_release 入库
failed：状态 + 错误可查；批量不阻塞后续任务
```

**批量队列**：`/api/files/batch` → N 条 `pending`；worker 限并发（如 2，对齐 01 §5.7）；单文件失败 → `pending_govern` 或 `failed`，不阻塞整体。

**失败/降级不丢数据**：解析失败 → `failed` + 原始文件保留；LLM 调用失败 → big→fast→纯规则→待人工；**互验冲突不自动选**，进治理（09）。

### 3.2 证据存储与归档（大批量存储管理）

证据 parquet 是"任何文件先存证"的产物，大批量（百万行 × 多文件）下会持续膨胀，需要生命周期管理：

| 阶段 | 策略 |
|---|---|
| 存储形态 | 只存**非空单元格**（`(sheet,row,col,raw_value)`，稀疏压缩，已实现） |
| 入库后压缩 | 接入完成且确认入库后，证据 parquet 转 zstd 压缩（体积约 1/3） |
| 归档 | 不再依赖证据的已接入文件，证据移入 `data/evidence_archive/`（按年目录），**原始上传文件默认长期保留（可配置保留策略，删除需审批）**（重跑只依赖原始文件） |
| 清理 | 归档满 N 年可删证据，但需保留 `intake_report` 配置（重跑链路 = 原始文件 + 确认配置，可完整复现） |

**原则**：证据可压缩/可归档/可删，**原始文件 + 确认后的配置永不删**——二者是完整重跑的最小集合。

## 4. LLM 识别不一致的覆盖策略（识别结果可能不一样）

LLM 输出天然有随机性（temperature=0 也不绝对稳定；7B 与 27B 结论可能冲突）。对策：**确定性 + 校验 + 仲裁 + 人工兜底**。

| 手段 | 说明 |
|---|---|
| 固定输入 | temperature=0 + 固定 prompt 模板 + 固定 schema |
| 结构化强校验 | 要求输出 JSON，解析失败自动重试 1 次，仍失败落"待人工"，不静默丢 |
| 关键决策仲裁 | 接入建议/低置信映射：fast/big 互验（Stage 3+）；**一致才可高置信展示，不一致只进人工**（禁止取多数/以 big 为准，00 C4） |
| 置信度分级 | 高置信可预填；**入库仍须 staging confirm**（C5）；低置信进人工确认清单 |
| 失败降级链 | big → fast → 纯规则 → 待人工（仅调用失败）；语义冲突不降级自动选 |
| 版本可追溯 | 每次识别记录：模型、参数、抽样范围、结果，入库可回溯"为什么这样识别" |

### 4.5 接入暂存（Staging）与影响评估（08-07 新增）

**问题**：一键接入直接改业务库有风险——模型建议/清洗配置可能有误，直接"入库"后出问题难回滚。参考成熟项目（excel-analysis-api）做法：**任何接入/变更先进暂存区，确认门（confirm）之后才真正写入**。

**暂存流程**（Step1~Step4 只产出建议，不碰业务库）：

```
Step1~Step4（画像/映射/质量/接入建议）产出建议
  │
  ▼
Staging（只读评估，mutates_state=false，不改任何真实状态）：
  ① gate preview      关键门禁预检：配置过白名单校验（05 §1）、必填字段齐全、region 边界合法
  ② format fingerprint 格式指纹：源文件哈希 + sheet 结构签名 + 表头快照，重跑同文件直接复用结论
  ③ deterministic recs 规则层建议（确定性，无 LLM）
  ④ model recs         模型建议（标注 model_state，01 §5.5）
  ⑤ assessment report  评估报告：将入库行数、关联成功率、冲突清单、异常清单
  ⑥ impact analysis    影响评估：将新增/更新/合并的物料与行数、疑似冲突清单
  ⑦ dry-run rebuild    干跑：在暂存副本上执行完整"清洗+关联+入库"，验证行数与质量
  │
  ▼
确认门：人工 confirm（需运维/治理 token，见 05 §1.5）
  → 仅调用 intake_release → writer（00 §3.1）
  → 写 release_manifest + write_audit
  → 禁止调用已退役的 POST /api/ingest
```

**与遗留管道关系**：历史「8 文件一键刷新」仅走 gated legacy ingest（05 §2.1），**新文件接入不得调用**。

**影响评估（impact analysis）**：
- 任何入库/主数据变更前，先在**暂存副本**上计算：将新增行数、将更新行数、将合并/重关联的物料数、疑似冲突清单（与 04 §7.2 冲突检测共用）。
- 全程只读（`mutates_state=false`），不改变任何真实状态；评估报告落 `intake_report`，可追溯"当时看了什么才确认的"。
- 人工基于影响评估决策：**接受 / 修改配置重跑 / 拒绝**——拒绝则原状不变，不产生任何残留。

**dry-run rebuild**：
- 在暂存表上跑完整"清洗 + 主数据关联 + 入库"，产出预入库结果（行数、关联率、异常数）。
- 与真实入库唯一区别：**不写业务库**；确认后重放暂存表到业务库，或直接带配置重跑（03 §3.2 最小重跑集合）。
- 配置修改后必须**重新 dry-run** 才能再次 confirm——确认门永远对着最新一次干跑结果，杜绝"改了配置直接入库"。

**format fingerprint 复用**：
- 指纹 = 文件哈希 + sheet 结构签名 + 表头快照；命中历史结论 → 直接复用该文件的确认配置与影响评估，跳过模型调用（省 LLM 开销）。
- 文件有变动（哈希/表头变化）→ 指纹失效，重新走暂存流程，历史结论仅作参考。

**API 形态**（对应 §5 扩展）：

| 方法 | 路径 | 功能 |
|---|---|---|
| POST | `/api/intake/stage/{file_id}` | 生成暂存评估（gate + fingerprint + 影响评估 + dry-run） |
| POST | `/api/intake/stage/{file_id}/confirm` | 确认门：写入业务库（必须先过 dry-run） |
| POST | `/api/intake/stage/{file_id}/discard` | 丢弃暂存，恢复原状 |
| GET | `/api/intake/stage/{file_id}` | 暂存评估报告（含影响评估与 dry-run 结果） |

### 4.6 发布清单（release_manifest，08-07 新增）

**问题**：dry-run/暂存确认后入库，但"哪些数据是正式发布的、哪些只是治理候选"要能区分——**`clean`/`blocked` 只是治理候选，不是正式发布**。

- `clean`（清洗后质量合格）与 `blocked`（质量异常 / 未映射 / 低置信）都先进暂存区，二者都是**治理候选**；只有确认门通过后，`clean` 才随 release_manifest 正式发布入库，`blocked` 留在治理中心待处理。
- 每次确认发布生成一条 release_manifest：

| 字段 | 说明 |
|---|---|
| `release_id` | 主键 |
| `file_id` / `config_version` | 源文件与确认的清洗配置版本（04 §6.7） |
| `staging_report_id` | 对应暂存评估报告（§4.5） |
| `clean_rows` / `blocked_rows` | 本次发布的干净行数 / 滞留治理行数 |
| `material_ops` | 主数据操作汇总（新增 / 合并 / 重关联数） |
| `released_by` / `released_at` | 发布人与时间（审计） |
| `fingerprint` | 格式指纹（复用 §4.5） |

- 发布即记录：`release_manifest` 与 `intake_report`、`govern_confirm` 关联，全链路可追溯。
- **回滚**见 §4.7 / 00 D6：按 release **血缘撤销与重建**，不做通用 reverse。

### 4.7 幂等发布与崩溃恢复（P0，对齐评审）

**问题**：confirm 同时触及 SQLite meta 与 DuckDB 业务库；重复点击、HTTP 重试或进程崩溃可能导致重复事实行或缺失 manifest。

**状态机（staging 记录）**：

```
STAGED →（条件更新仅一次成功）→ RELEASING → RELEASED
                              ↘ FAILED（可补偿）
```

| 规则 | 说明 |
|---|---|
| `release_id` | 全链路唯一；事实行带 `source_release_id` |
| 幂等键 | `(source_file_hash, config_version, target_domain)` 唯一约束 |
| confirm | 仅当状态为 `STAGED` 时 CAS 转为 `RELEASING`；否则 **409** |
| 业务写入 | writer 按 `release_id` **delete-and-replace 或等价 merge**，重复执行结果相同 |
| 启动补偿 | 扫描 `RELEASING`：对照业务库行数完成 → `RELEASED`，或清理半写入后标 `FAILED` 待重试 |
| 执行者 | 仅 **writer service**（00 D2）；API 只发发布命令 |

### 4.8 血缘回滚（D6）

- 保留：原始文件、确认配置、`release_id`、事实行 `source_release_id`。
- 回滚 = **撤销目标 release 的派生行** → 按指定规则/配置版本 **重新生成**（lineage_rebuild）。
- 不实现「通用 reverse 操作」幻想（主数据合并/重关联通常不可逆推）。

## 5. 落地的 API 设计

| 方法 | 路径 | 功能 | 用模型 |
|---|---|---|---|
| POST | `/api/files` | 上传 → 异步解析证据（202 + task_id） | 否（后台任务） |
| POST | `/api/files/batch` | 批量上传 → N 个任务排队处理 | 否（后台任务） |
| GET | `/api/tasks/{task_id}` | 轮询任务状态/进度（intake_task） | - |
| POST | `/api/intake/analyze` | 一键编排：画像+映射+质量+接入建议 | fast/big + embed |
| POST | `/api/intake/profile/{file_id}` | 单步：文件画像 | fast |
| POST | `/api/intake/plan/{file_id}` | 单步：接入建议（含质量预检） | big |
| GET | `/api/intake/report/{file_id}` | 完整接入报告（各步结论+证据） | - |
| POST | `/api/intake/stage/{file_id}` | 生成暂存评估（gate+指纹+影响评估+dry-run，§4.5） | 否（规则） |
| GET | `/api/intake/stage/{file_id}` | 暂存评估报告（含影响评估与 dry-run 结果） | - |
| POST | `/api/intake/stage/{file_id}/confirm` | 确认门 → writer 幂等发布（§4.5/§4.7） | 否 |
| POST | `/api/intake/stage/{file_id}/discard` | 丢弃暂存，恢复原状 | 否 |

编排结果落 **SQLite meta** 的 `intake_report` / `intake_task`；confirm 只触发 writer，不由 API 直写 DuckDB。
