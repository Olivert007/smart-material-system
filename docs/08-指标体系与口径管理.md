# 模块 08 · 指标体系与口径管理

> 定位：业务"数量 / 金额 / 汇总"口径多、叫法乱，问答与汇总表对齐都容易**口径混淆**。
> 本模块用**指标字典**把口径显式化、可审计、可演进，并贯穿问答（02）、接入（03）、治理（04）、界面（07）。
> 版本：Phase 2.2（2026-08-08）：口径校验为模板/结构约束，放弃通用语义等价；指标写须 ops（05 §1.5）。

---

## 1. 问题定义

同样的中文问法，不同人口径不同：

| 问法 | 歧义点 |
|---|---|
| 库存总金额是多少 | `stock_value` 是含税还是不含税？含临时库 / 在途？ |
| 需求总量是多少 | 含全部期次还是本期？含已取消项？ |
| 资产一共多少台 | 含待报废 / 有问题状态吗？含历史副本吗？ |
| 汇总表数量 vs 明细表数量对不上 | 是口径不同（汇总含预留、明细不含），还是数据问题？ |

**不建指标字典时**：每次问答靠 LLM 猜口径，T0 的 SQL 合法但语义可能错（02 §6.5 数值校验只能发现明显异常）；汇总表与明细对不上时人工凭经验判断——不可审计、不可复用。

**建指标字典后**：口径成为**声明式资产**（与 03 清洗配置同一思路）——定义一次、注入所有问答、双向校验汇总表、可版本演进。

## 2. 指标字典表 `metric_dict`（meta.sqlite）

| 列 | 说明 |
|---|---|
| `metric_id` | 指标编码（如 `INV_VALUE_TOTAL`） |
| `metric_name` | 指标名（如 库存总金额） |
| `aliases` | 同义叫法（金额、库存金额、总额），供问题匹配 |
| `unit` | 单位（元 / 件 / 台） |
| `definition` | 口径说明（含税与否、含哪些状态、时间范围） |
| `definition_sql` | **口径基准 SQL**（可执行的 SELECT，见 §3） |
| `drilldown_template` | 可选下钻模板（占位符 `{{dim}}` / `{{dim_col}}` / `{{dim_val}}`） |
| `source_tables` | 来源表 / 列 |
| `dimensions` / `allowed_dimensions` | 可下钻维度白名单（区域 / 分类 / 时间 / 状态） |
| `status` | `active` / `deprecated` |
| `version` | 版本号（变更 +1，历史留存） |
| `confirmed_by` / `created_at` / `updated_at` | 审计 |

核心原则：**指标一经定义，SQL 只能以 `definition_sql` 为基准生成或下钻**，不允许模型自由发挥口径。

## 3. 指标定义示例（与现有 6 表对应；种子 SQL 见 `app/services/metrics/metrics.py`）

| 指标 | 口径 SQL（definition_sql） | 口径说明 |
|---|---|---|
| 库存总数量 `INV_QTY_TOTAL` | `SELECT SUM(stock_qty) AS v FROM fact_inventory` | 现有库存合计；单位件（active） |
| 库存记录数 `INV_RECORD_CNT` | `SELECT COUNT(*) AS v FROM fact_inventory` | 库存台账行数（active） |
| 库存总金额 `INV_VALUE_TOTAL` | `SELECT SUM(stock_value) AS v FROM fact_inventory WHERE stock_value IS NOT NULL` | 数量×单价；**排除空值**（schema 无 `is_temp_warehouse` 列，不做临时库过滤）。**台账无金额列 → 无有效数据，`data_status=no_data`（§3.1）** |
| 需求总量 `DEMAND_QTY_TOTAL` | `SELECT SUM(quantity) AS v FROM fact_demand` | 全部期次需求合计，含已确认与计划（active） |
| 资产总数 `ASSET_COUNT_TOTAL` | `SELECT COUNT(*) AS v FROM fact_asset WHERE COALESCE(status, '') NOT LIKE '%待报废%'` | 排除状态含「待报废」（active） |
| 出入库总量 `FLOW_QTY_TOTAL` | `SELECT SUM(quantity) AS v FROM fact_stock_flow WHERE flow_type='IN'` | 仅入库流水合计；**draft，激活前置**见下方与 [12 §8](12-出入库流水解析.md) |

- 每个指标可配下钻维度；下钻须与基准同过滤条件。
- **可执行测试（激活门禁）**：每条 `active` 指标必须附带固定输入夹具、期望值、容差、适用 `version`；测试通过才允许 `status=active`。文字说明与 SQL 不一致视为缺陷（评审 P1-4）。
- **`FLOW_*` 额外前置（12）**：目标来源流水规则路径已跑通；无「年份当 quantity」抽检问题；勾稽任务可跑通且差异清单可导出（**不要求差异为零**）；错误历史流水已血缘重建。未满足时指标保持 `draft`，问答优先提示「流水质量未达标」。
- LLM 不直接写字典（05 §1）。

可选配套（可 `draft`）：`FLOW_PARSE_L1_RATIO`、`FLOW_RECONCILE_GAP_CNT`（定义见 12 §8）。

### 3.1 金额勾稽口径（中危 1 方案 B，2026-08-10 拍板）

- 台账录入批**无金额列**，金额汇总勾稽**不做硬核验**；勾稽仅覆盖数量（12 FL6：`ΣIN−ΣOUT ≟ stock_qty − opening_qty`）。
- `INV_VALUE_TOTAL` 依赖 `stock_value` 列；台账未提供该列时无有效数据，`evaluate_metric` 返回 `data_status=no_data`，前端显示「暂无数据」（U-3），**不得**按 0 展示。
- 若业务后续补「单价/合价」列（方案 A 可随时启用），仅需映射 + `value_rule`，指标 SQL 不变。

## 4. 口径冲突检测（规则，不耗 LLM）

| 冲突 | 检测规则 | 处理 |
|---|---|---|
| 同一指标名被定义多次 | `metric_name` 唯一；新定义只改 version | 仅 `active` 生效，旧版本留存审计 |
| 同义叫法指向多个指标 | `aliases` 与指标 `metric_name`/`aliases` 互相匹配 | 标记 `conflict`，进治理中心人工确认归属 |
| **汇总表 vs 明细表不一致** | 03 `summary` 角色识别后，把汇总表数值列与指标字典匹配（§6）；对得上时执行"汇总值 vs 指标 SQL 值"对比 | 差异 > 容差 → 标记口径冲突，提示人工确认"口径不同 or 数据问题"，确认结论回写指标字典 |
| 数值校验越界 | 02 §6.5 数值范围检查与指标字典基准值对比 | 超阈值 → warning 提示疑似口径错误 |

## 5. 问答注入（与 02 衔接）

**不追求通用「SQL 语义等价」**（不可判定且易误拦下钻）。改为**模板参数化**：

| 概念 | 定义 |
|---|---|
| `definition_sql` | 指标基准 SELECT（无动态维度，或仅含固定过滤） |
| `drilldown_template` | 可选；带占位符的下钻模板，如在基准上追加 `GROUP BY {{dim}}` / `AND {{dim_col}} = {{dim_val}}` |
| `allowed_dimensions` | 允许注入的维度列白名单（∈ information_schema） |

```
用户提问
  │
  ▼
① 指标匹配（规则）：命中 metric_name / aliases → 候选指标（多候选冲突 → 待人工，C4）
  │ 命中唯一
  ▼
② 注入 prompt：definition + definition_sql + allowed_dimensions + drilldown_template
  │
  ▼
③ 生成 SQL 后做「口径结构校验」（规则，非语义等价）：
   - 必须通过 05 §1.1 SQL 防线与 02 标识符白名单
   - 聚合列 / 核心过滤条件必须与 definition_sql 一致（解析 AST 或规范化文本包含必选片段）
   - 若含 GROUP BY / 额外 WHERE：维度列必须 ∈ allowed_dimensions；不得改换聚合度量列
   - 或：直接选用 drilldown_template 填参生成（优先路径，少靠模型自由发挥）
  │ 不通过
  ▼
④ 拦截 → 提示基于指标口径重试 1 次；仍失败 → 待人工（返回候选模板 SQL）
```

- 未命中指标字典 → 走 02 全流程（无口径结构校验）。
- 命中后**优先模板填参**，LLM 只负责选指标/维度/时间措辞；校验失败不静默放行。
## 6. 汇总表对齐（与 03 衔接）

03 §1.2 把 `summary` 角色从"一刀切 report_only"改为"可入库 / 仅参考 / 与明细一致性校验"。本模块补齐**汇总表 ↔ 指标**对齐：

```
03 Step3 识别出汇总表
  │
  ▼
① 数值列 ↔ 指标字典匹配（列名/表头归一化命中，复用 04 字典四层匹配）
  │
  ▼
② 产出候选映射 "汇总表列 ↔ 指标"，人工确认（治理中心）
  │
  ▼
③ 确认后：定期执行"汇总值 vs 指标 SQL 值"对比（§4 冲突检测）
      ├─ 一致 → 汇总表可作为指标的旁证来源（双写校验）
      └─ 不一致 → 口径冲突，人工判定后回写指标字典或标记数据问题
```

- 好处：汇总表从"没用的参考"变成**指标的可信校验源**；明细与汇总双向对账，任何一方漂移都能被发现。

## 7. 生命周期与自学习

- **定义**：人工在治理中心新增指标（name/aliases/口径 SQL/维度），`version=1`。
- **变更**：口径调整走人工确认，新 version 生效，旧 version 置 `deprecated`（历史查询与报告仍可追溯）。
- **回写**：口径冲突的人工判定、问答修正的 SQL（02 §6.1 few-shot）同步回写指标字典与 few-shot 池——与 04 自学习同一套"人工修正即资产"机制。
- **边界**：指标字典是**约束不是推理结果**；LLM 永远不能直接修改指标定义。

## 8. API 与界面（与 07 衔接）

| 方法 | 路径 | 功能 | 依赖 LLM |
|---|---|---|---|
| POST | `/api/metrics` | 新增/修改指标（人工，version+1） | 否 |
| GET | `/api/metrics` | 指标字典列表（含 status/version） | 否 |
| GET | `/api/metrics/{id}` | 指标详情（definition_sql 可执行） | 否 |
| POST | `/api/metrics/check` | 口径冲突检测（含汇总表对比） | 否（规则） |
| POST | `/api/metrics/match` | 问题文本 → 候选指标 | 否（规则匹配） |

界面落点：[07 §3.8 指标字典](07-界面层设计.md)（独立页，非治理中心子 Tab）：列表 / 定义编辑 / 冲突清单 / 汇总对齐。
