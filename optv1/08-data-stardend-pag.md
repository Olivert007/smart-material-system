# 08数据规整页面专项评审与修改方案
## 文档目的
本文专项评审“数据规整/治理待办"页面的问题，并给出面向后续开发Agent的修改方案。
重点包括：
页面当前表达问题。
用户真正需要看到的信息。
推荐页面结构。
关键术语定义。
命名修改建议。
页面接口要求。
状态、权限和发布约束。
本文不替代docs/中的正式架构和安全规范。若本文与“`docs/`、ADR或后端接口契约冲突，以正式规范为准。
# 总体结论
当前数据规整页面想表达的信息很多，但没有形成用户能理解的主线。
页面应该先回答：
当前有没有可规整数据？
当前数据能不能用？
为什么不能用？
用户下一步应该做什么？
哪些问题会阻塞数据成果？
然后再展示：
字段规整。
物资规整。
单位口径。
异常处理。
AI建议。
规则和历史。
库存对账。
当前页面的问题是先展示治理能力和功能Tab，导致用户看不出重点。
## 当前页面问题
### 1. 没有优先判断是否有数据
当前系统没有业务数据时，页面仍展示完整的治理模块、待办总览和Tab。
用户会困惑：
>没有数据，为什么让我看字段规整、规则学习、流水解析？
正确做法：
没有接入文件时，显示空状态。
没有staging时，引导去数据接入。
没有可用数据时，解释为什么还不能查看成果。
### 2. 技术code暴露给用户
页面中可能出现类似：
..`text
rule_path_has_published_rows
这类code是系统内部门禁标识，用户无法理解。
应转换为业务语言：
."`text
当前没有已发布的出入库流水，库存对账相关指标暂不可用。
技术code可以保留在高级详情里，但不能作为主文案。

## 3. “治理待办概念重复
页面标题、卡片标题和Tab中都可能出现“治理待办”，造成结构重复。
应统一主标题为：
""`text
数据规整工作台
页面内部再使用：
..`text
当前待处理事项
避免重复堆叠同一概念。
### 4. 0状态没有解释
当待确认字段、待匹配物资、待解析流水都是时，用户不知道这是：
系统正常。
没有数据。
数据未解析。
功能未跑起来。
状态必须附带原因
例如：
."`text
当前没有治理待办，因为还没有接入可规整数据。
或：
`text
当前没有治理待办，最近一次规整已通过门禁。
## 5. Tab命名偏专业和技术
当前类似命名：
规则学习。
流水解析。
勾稽差异。
对普通业务用户不直观。
建议：
- 规则学习规则沉定或放入“规则与历史高级区。
- 流水解析出入库记录处理。
- 勾稽差异库存对账或“出入库与库存对账
术语定义
非数据规整
将原始文件中的字段、物资、单位、数量、分类和备注等内容，整理为统一、可信、可追潮的数据结构。
数据规整不是简单清洗，也不是直接问数。
# 治理待办
系统不能自动确认、需要人工处理的事项。

包括：
字段低置信。
物资无法匹配。
单位无法换算。
数量异常。
AI建议待确认。
规则冲突。
发布门禁阻塞。
### 可用数据
通过当前质量门禁，可以展示、导出或问数的数据。
约束：
- 可用数据不等于正式发布数据
- 可用数据不等于库存事实。
## 阻塞数据
因字段、物资、单位、数量、规则或人工确认缺失，不能进入可用结果的数据。
非规则沉淀
人工确认后，将某些字段映射、物资匹配或异常处理方式保存为后续可复用规则。
约束：
- 单次确认不一定自动成为全局规则。
- 全局规则启用前必须预演影响。
## 库存对账
原“勾稽差异"的用户化命名。
含义：
...text
现有库存是否等于初始库存+入库数量-出库数量
如果对不上，就是库存对账差异。
不建议使用“勾稽差异“作为普通用户页面命名，因为它过于审计化和专业化。
# 推荐页面结构
# 第一层：当前状态
页面顶部应先显示当前数据状态。
状态包括：
- no_data：没有接入数据。
- parsing：正在识别结构。
- needs_standardization需要规整。
- blocked：存在阻塞。
- ready：当前可用。
- published：已有发布版本。
不同状态展示不同主文案。
#### 无数据状态
标题：
"`text
当前没有可规整数据

说明：
..`text
请先在“数据接入”上传原始需求表或台账文件。系统完成结构识别后，会在这里显示字段、物资、单位和异常治理待办。
主动作：
"`text
去数据接入
此时不展示复杂治理Tab。
#### 有阻塞状态
标题：
当前数据暂不可用
说明：
`text
部分记录未通过质量门禁，请先处理字段、物资、单位或数量问题。
应展示：
- 阻塞记录数。
- 主要阻塞原因。
- 最优先处理事项。
-处理入口。
#### 可用状态
标题：
""`text
当前数据可用
应展示：
- 可用记录数。
- 阻塞记录数。
- 最近规整批次。
- 查看数据成果。
- 查看追溯审计。
## 第二层：下一步动作
页面必须给出清晰下一步，而不是只展示能力。
动作示例：
- 去数据接入。
- 处理字段映射。
- 处理物资匹配。
- 查看阻塞数据。
- 审核AI建议。
-查看数据成果。
-查看追溯审计。
## 第三层：当前待处理事项
以待办列表作为主区域。

每条待办应包含：
待办类型。
问题说明。
影响记录数。
来源文件。
来源Sheet。
系统建议。
置信度。
可执行动作。
待办排序：
- 1.发布阻断。
- 2.影响记录数最多。
- 3.关键字段缺失。
- 4.低置信但可快速确认。
- 5.AI建议待审核。
## 第四层：按需展开处理详情
规整能力不应作为常驻大卡片展示。用户点击某个待办或状态卡后，再展开对应处理详情。
详情包括：
字段规整。
规则沉淀。
物资主数据。
出入库记录处理。
库存对账。
约束：
- 第一屏不默认展开详情
- 详情区必须带明确标题，例如处理详情：字段规整
- 处理完成后，应提示用户返回上方刷新待办数量。
常第五层：高级能力下沉
以下功能不应作为普通用户第一屏入口：
规则字典。
-规则历史。
指标口径。
模型状态。
运维设置。
这些能力可以放在详情内部、系统设置或后续亮级入口中，不应与待办主路径并列。
# 推荐页面布局
最新推荐布局：
"text
数据规整工作台
[顶部状态说明]
一句话说明本页用于处理字段、物资、出入库和库存对账问题
刷新按钮
[当前待处理事项]
状态数字：待确认字段/待匹配物资/待解析流水/门禁阻断
待办列表，按影响排序
每行给出处理入口
[处理详情，默认收起]
用户点击待办后展开
只显示当前选中的处理类型
不再推荐常驻展示多排Tab、大流程卡片或高级能力卡片。

"has_staging":false,

text

`text
QUALITY_BLOCKING

text
部分记录未通过质量门禁，请先处理阻塞问题。
text
NO_COLUMNS

"`text
部分工作表没有识别到可用字段，需要确认是否跳过或补充映射。
text
MAP_PENDING
用户文案：
"`text
仍有字段映射需要人工确认。

## 命名修改建议
### 页面名称
建议：
- 数据规整与治理待办 -> 数据规整工作台
### 区域名称
建议：
- 治理待办总览当前待处理事项
- 规则学习规则沉淀
- 流水解析出入库记录处理
- 勾稽差异
### 不建议使用
勾稽差异。
机器不确定项。
规则学习候选。
发布业务库。
运维确认发布。
这些词偏技术或偏内部流程，普通用户不易理解。
## 权限约束
普通业务用户：
可以查看当前状态。
可以查看待办摘要。
可以进入允许处理的待办。
不应看到模型endpoint、原始JSON、系统任务事件。
数据治理人员：
可以处理字段、物资、单位、异常和AI建议。
可以查看规则与历史。
可以预演规则影响。
管理员：
可以查看高级治理工具。
可以进行系统设置和运维操作。
约束：
- 前端隐藏按钮不等于权限控制。
- 服务端必须校验权限。
actor不能由客户端payload定义。
## 发布与数据状态约束
上传成功不等于解析完成。
解析完成不等于数据可用。
规整暂存不等于写入标准表。
可用数据不等于正式发布数据。
下载结果不等于发布。
AI建议不等于已确认。
忽略异常不等于修复异常。
## 前端实现建议
### 空状态优先
且没有staging或发布数据时：
recent_files.length ===0
显示空状态。
显示去数据接入按钮。
隐藏治理处理区。
可显示简短三步说明：先接入文件、系统识别结构、人工确认后形成成果。

### 阻塞状态优先
或存在“blocked_rows>θ”：
显示阻塞原因。
显示待处理事项。
技术code转换为文案。
### 详情按需展开
不要默认展开字段、物资、出入库、库存对账等处理界面。
推荐交互：
第一屏只展示当前待处理事项。
点击状态数字或待办行的处理按钮后，展开对应处理详情。
用户可以收起详情，回到待办列表。
### 避免重复Tab
不要同时出现：
页面标题：治理待办。
卡片标题：治理待办总览。
外层Tab：当前待办/规则与历史/指标口径。
内层Tab：字段规整/规则沉淀/物资主数据。
建议只保留一个核心页面标题和一层业务处理入口。
## 验收标准
页面改造完成后，用户应能在10秒内回答：
当前有没有数据？
当前数据能不能用？
为什么不能用？
下一步应该点哪里？
哪个问题影响最大？
哪些内容是AI建议？
哪些数据仍被阻塞？
规整后的成果在哪里？
若用户仍然需要解释规则学习勾稽差异"rule_path_has_published_rows"等术语，说明页面还没有达标。
## 实施顺序
- 1.将页面标题改为“数据规整工作台”。
- 2.增加no_data空状态。
- 3.将技术code转换为用户文案。
- 4.将“治理待办总览”改为“当前待处理事项”
- 5.以待办列表替代功能Tab作为主区域。
- 6.将“勾稽差异"改为“库存对账”。
- 7.移除外层二级Tab，避免出现两排页面入口。
- 8.去掉常驻规整能力大卡片，避免第一屏被功能说明淹没。
- 9.将处理详情默认收起，点击待办后再展开。
- 10.后续再沉淀统一summary/todos接口。
## 当前代码实现状态
截至本次修改（2026-08），前端已实现：
- GovernHub.vue 使用“数据规整工作台”作为主标题。
- 无数据时展示空状态和“去数据接入”主动作。
- 有数据时第一屏只展示顶部说明和“当前待处理事项”。
- 已移除外层“当前待办 / 规则与历史 / 指标口径”二级 Tab。
- 已移除常驻的规整能力说明大卡片；高级能力下沉到默认收起的折叠区。
- 处理详情默认收起，点击待办后展开，处理完成后提示刷新。
- 规则学习 → 规则沉淀；流水解析 → 出入库记录处理；勾稽差异 → 库存对账。
- 技术 code → 用户文案映射同时在后端 todo_board.gate_label 与前端 gateLabels.ts 生效，
  例如 rule_path_has_published_rows → “当前没有已发布的出入库流水，库存对账相关指标暂不可用”。

后端已实现（原“仍未实现”三项已落地，并有测试覆盖 tests/test_todo_board_08.py）：
- GET /api/v1/govern/standardization/summary：统一状态汇总；state 由数据状态推导（no_data /
  parsing / needs_standardization / blocked / ready / published），返回状态文案、
  next_actions、empty_reason 与门禁信息。实现见 app/api/routers/govern.py 与
  app/services/govern/todo_board.py。
- GET /api/v1/govern/todos：统一待办列表，按影响排序；异常按 reason_code+file_id 聚合，
  字段待办按表头统计影响行，出入库按 file_id+source_sheet+flow_type 聚合；每条待办返回
  来源文件、来源 Sheet、置信度、影响行数与乐观锁版本号。
- POST /api/v1/govern/todos/{todo_id}/decision：统一决策入口（accept | amend | reject |
  ignore，支持 dry_run 影响预演），幂等、审计、actor 服务端注入均已实现，并校验
  expected_version（不匹配返回 409 版本冲突）。

保留事项：
- /todos 与 /govern 双入口：/todos 页面标题仍为“治理待办”、区域为“治理待办队列”，
  属有意保留的入口设计；如需严格消除概念重复，可将 /todos 入口统一为“数据规整工作台”。
- summary 中“clean_rows”“最近规整批次”等建议字段未单独返回（可由现有接口组合），
  不影响状态与待办主路径。
