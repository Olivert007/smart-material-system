# 06治理中心与系统页面评审

## 文档目的
本文从用户视角评审“治理中心"和“系统页面”的合理性，明确问题、修改方法、页面接口、权限约束和阶段限制。
和已接受ADR为准。
本文用于后续开发Agent改造页面时参考。它不替代docs/中的正式架构、安全和API规范；若发生冲突，以docs/

## 总体结论
更合理的页面职责是：
治理中心：处理数据规整过程中的不确定项、阻塞项和人工确认。
系统页面：检查运行状态、模型状态、配置、备份和管理员设置。
追溯审计：承载血缘、审计和结果来源解释，不应混在系统设置中。

## 当前问题

### 治理中心的问题
当前治理中心包含：
治理待办。
规则与主数据。
指标口径。
字段规整。
规则学习。
物资主数据。
流水解析。
勾稽差异。
这些能力本身有价值，但组织方式仍偏功能模块。普通用户进入后不一定知道：
哪些问题正在阻塞数据可用。
哪个问题最应该优先处理。
处理一个待办会释放多少数据。
AI建议是否已经被采纳。
规则变更会影响哪些历史数据。
核心问题：
- 页面按系统功能拆分，而不是按用户待办拆分。
- 用户需要理解“规则学习”流水解析”勾稽差异”等治理术语。
- 待办优先级不够清楚。
- 高级规则、历史、指标口径和日常待办混在一起。

### 系统页面的问题
当前系统页包含：
运维面板。
本地模型状态。
版本血缘。
审计追溯。
指标维护。
设置。
这些内容面向的用户不同：
运维人员需要API、worker、模型、磁盘、备份和配置。
治理人员需要规则、指标口径、血缘和审计。
业务用户只需要知道数据状态、待办和结果来源。
核心问题：
- 系统页混合了运维、治理、追溯和配置。
- 血缘和审计是业务信任能力，不应藏在系统管理中。
- 指标维护属于口径治理，不应放在系统设置里。
- 模型状态是运维能力，AI建议审核才是业务能力。

## 推荐页面职责

### 治理中心
治理中心应回答：
哪些问题需要我处理？
哪些问题影响最大？
系统建议怎么处理？
我采纳、修改或拒绝后会发生什么？
哪些处理会形成规则？
治理中心不应默认回答：
模型endpoint是什么。
API是否在线。
备份是否成功。
原始JSON是什么。
内部任务事件是什么。

### 系统页面
系统页面应回答：
系统是否ready？
API、worker、数据库、前端产物是否正常？
本地模型是否可用？
模型不可用影响哪些建议能力？
最近备份和恢复状态如何？
运行配置和管理员设置是否正确？
系统页面不应承载：
普通业务用户的治理待办。
结果血缘的主要入口。
审计追溯的主要入口。
指标口径的业务维护主入口。

### 追溯审计
追溯审计应回答：
某条结果来自哪个源文件、Sheet和行？
哪条规则或确认影响了它？
谁在什么时候确认了什么？
这次发布或导出对应哪个数据版本？
追溯审计可以从数据成果、治理待办、规则历史和发布结果中跳转进入。

## 治理中心修改方法

### 第一层：治理待办总览
默认进入治理中心时，优先展示待办总览。
应展示：
- 待确认字段数。
- 待匹配物资数。
- 待处理异常数。
- 待审核AI建议数。
- 规则冲突数。
- 发布阻断项数。
- 每类待办影响的记录数。
排序规则：
优先发布阻断项。
优先影响可用数据最多的项。
优先关键字段缺失或冲突。
优先低置信但可快速确认项。
页面动作：
- 采纳。
- 修改后采纳。
- 拒绝。
- 忽略。
- 查看证据。
- 预演影响。
- 重新规整。

### 第二层：按治理对象分区
治理中心内部可保留分区，但应服务待办处理：
字段规整。
物资规整。
单位与口径。
异常处理。
AI建议审核。
规则与历史。
不建议默认把“规则学习”作为普通用户入口。它应作为“规则与历史”的高级功能。

### 第三层：高级治理工具
以下内容应折叠或放入高级区：
规则学习候选。
规则字典。
确认历史。
指标口径维护。
流水解析细节。
勾稽差异细节。
这些能力有价值，但不应阻断普通用户理解待办主线。

## 系统页面修改方法

### 保留在系统页面
系统页只保留管理员和运维能力：
系统健康。
APIready。
worker状态。
数据库状态。
前端构建产物状态。
本地模型状态。
磁盘和数据目录。
备份和恢复状态。
运行配置。
管理员设置。

### 移出系统页面
以下内容不应作为系统页主Tab：
版本血缘。
审计时间线。
指标维护。
AI建议审核。
推荐迁移：
版本血缘 -> 追溯审计。
审计时间线 -> 追溯审计。
指标维护 -> 规则与口径/数据规整高级区。
AI建议审核 -> 治理中心。

### 模型页表达
系统页可以保留“本地模型状态”，但它应面向运维。
普通用户不需要看到：
endpoint。
端口。
raw model id。
token数。
prompt
temperature
原始响应。
默认只展示：
模型是否可用。
哪些能力受影响。
是否已降级到规则路径。
最近错误摘要。
高级详情再展示endpoint和错误堆栈。

## 页面接口要求

### 治理中心接口
后续改造建议增加或整理以下接口语义。具体路径可沿用现有/api/v1风格。

#### 待办汇总
用途：
返回治理中心顶部总览。
建议响应字段：
map_pending_count
material_pending_count
exception_pending_count
ai_suggestion_pending_count
rule_conflict_count
release_blocker_count
blocked_rows
affected_rows
next_actions
约束：
- 只返回汇总，不返回大段原始证据。
- 每个数量必须可追溯到具体队列或质量报告。

#### 待办列表
用途：
按影响范围返回可处理事项。
建议响应字段：
todo_id
todo_type
title
status
severity
affected_rows
source_file
source_sheet
suggestion
confidence
actions
requires_review
约束：
- AI建议必须标记来源。
- 批量动作前必须能预演影响。
- 不能把ignore表达成修复。

#### 待办处理
用途：
采纳、修正、拒绝或忽略待办。
建议请求字段：
todo_id`
decision
amended_value
note
expected_version
idempotency_key
约束：
- 必须校验版本。
- 必须幂等。
- 必须写审计。
- actor由服务端注入，不能由客户端payload传入。

### 系统页面接口

#### 系统ready
用途：
展示系统是否可用于业务操作。
建议包含：
- API live
- API ready。
- meta DB
- biz DB
- worker
- frontend dist
- data dir。
- backup status
约束：
- 页面应优先显示ready，而不是只显示live。
- live只表示进程存活，不代表系统可用。

#### 模型状态
用途：
展示本地模型是否可用及影响范围。
建议包含：
- role
- configured_model
- ok
- endpoint
- fallback
- affected_features
- last_error
约束：
- 普通视图隐藏endpoint。
- 模型不可用不得阻断规则路径。
- 模型不可用时，相关AI建议进入待审核或降级状态。

#### 审计与血缘
审计与血缘接口可以继续存在，但主入口不应在系统设置。
约束：
- 审计记录只追加。
- 支持按业务对象查询。
- 支持从数据成果反向进入。

## 权限与角色约束

### 普通业务用户
可访问：
- 工作台。
- 数据接入。
- 数据成果。
- 问数助手。
- 部分治理待办。
不应默认访问：
- 系统设置。
- 模型endpoint。
- 备份配置。
- 运行配置。
- 原始系统日志。

### 数据治理人员
可访问：
- 治理待办。
- 数据规整。
- 规则与历史。
- 指标口径。
- 追溯审计。
限制：
- 规则变更必须预演。
- 关键处理必须审计。
- 批量操作必须展示影响范围。

### 管理员/运维
可访问：
- 系统设置。
- 本地模型状态。
- 运维面板。
- 备份恢复。
- 配置。
限制：
- 运维操作不应绕过业务治理门禁。
- 模型重启或配置变化应记录审计。
- 客户端角色不能作为真实授权依据。

## 关键限制
治理中心不能变成技术配置页。
系统页面不能承载普通业务流程。
AI建议审核不属于系统设置。
血缘和审计不应被藏在系统设置里。
指标口径不应和运维配置混在一起。
模型状态不等于AI建议已经可信。
API live不等于系统ready。
隐藏按钮不等于权限控制。

## 验收标准
治理中心改造后，用户应能回答：
当前有多少治理待办？
哪些待办正在阻塞数据可用？
哪个待办最应该先处理？
处理后影响多少记录？
哪些建议来自AI？
哪些规则会被沉淀或变更？
系统页面改造后，管理员应能回答：
系统是否ready？
API、worker、数据库是否正常？
本地模型是否可用？
模型不可用影响哪些功能？
最近备份和恢复状态如何？
当前配置是否适合本地受控部署？
普通业务用户不应被迫回答：
模型endpoint是什么。
worker当前线程状态是什么。
rawJSON是什么。
SQL表名是什么。
审计表结构是什么。

## 建议实施顺序
1.治理中心先加待办总览和影响排序。
2.将规则学习、规则资产、指标维护降级为高级区。
3.将系统页中的血缘和审计迁移到追溯审计。
4.将模型页改为运维状态页，业务侧只保留AI建议审核。
5.系统页健康检查切换到ready语义。
6.补充治理待办处理的版本、幂等和审计约束。
完成以上改造后，再考虑视觉优化和组件拆分。
