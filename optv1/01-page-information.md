# 01 页面信息架构改造

## 当前页面结构
当前前端主导航为：
- 看数：总览、问数、数据中心
- 接入：接入与任务。
- 治理：治理中心。
- 系统：系统。
旧入口如 `browse`、`reports`、`metrics`、`models`、`ops`、`lineage`、`audit`、`settings`已经重定向到新的聚合页面。这说明系统已经开始收敛页面数量，但页面心智仍偏向系统能力集合。

## 主要问题

### “看数"前置过早问数和数据中心现在放在很靠前的位置，但对业务用户来说，数据尚未规整之前，问数和报表的可信度并不高。
风险：
- 用户误以为上传原始数据后就可以直接问数。
- 用户忽略字段、物资、单位、异常等治理问题。
- 问数结果被理解成正式结果，但它可能只来自候选数据或未发布数据。
调整建议：
- 问数仍保留，但定位为“基于可用数据的辅助查询”。
- 数据中心改名为“数据成果”。
- 在数据未规整完成时，问数页面应提示数据状态和限制。
- ###“治理中心"过于抽象治理中心目前包含待确认、规则资产、指标口径。对熟悉系统的人有意义，但普通用户不容易理解自己应该做什么。
风险：
- 用户不知道“待确认”是字段、异常、AI建议还是规则冲突。
- 规则资产和指标口径混在治理中心，会让普通处理流程变重。
- 用户无法按影响范围决定优先处理哪个问题。
调整建议：
- 将治理中心改为“治理待办”或“数据治理”
- 默认展示待办队列，而不是功能Tab。
- 待办按影响范围排序，例如影响记录数、阻塞关键字段、是否影响导出。
- ###“数据规整”缺少独立位置系统核心价值应是把混乱数据规整为统一、可信、可追溯的数据。但当前导航没有明确的“数据规整”入口。
风险：
- 字段映射、单位换算、物资匹配、分类归一、异常处理散落在不同页面。
- 用户无法建立“规整前 -> 规整后”的心智。
- 大模型问数容易抢占产品表达。
调整建议：
- 新增或突出“数据规整”主入口
- 将字段、物资、单位、分类、口径、主数据对齐归入该入口。
- 将异常、低置信、AI建议作为规整过程中的待办。
- ###“系统”内容过多且混杂系统页包含运维面板、模型管理、版本血缘、审计时间线、指标维护和设置。其中有些是运维能力，有些是业务追溯能力，有些是治理配置能力。
风险：
- 业务用户需要看血缘或审计时，被迫进入系统管理。
- 模型管理、设置和运维信息暴露过多。
- 指标维护同时出现在治理和系统语境中，角色边界不清楚。
调整建议：
- 系统页只保留运维、模型健康、设置、备份、环境检查。
- 血缘和审计移到“追溯审计”。
- 指标口径移到“数据规整”或“治理规则”高级区。
- ##推荐主导航
- ###1.工作台
用户问题：
- 当前数据能不能用？
- 为什么不能全部用？
- 现在最应该处理什么？
- 处理后能释放多少可用数据？
页面内容：
- 可用记录数、阻塞记录数、待处理问题数。
- 最优先治理待办。
- 最近接入文件状态。
- 数据成果入口。
异常和阻塞原因摘要。
约束：
- 不展示原始JSON。
- 不展示模型endpoint。
- 不把“可用数据”称为“最终数据”。
- 不把当前下载结果称为正式发布。
- ###2.数据接入
用户问题：
- 我该上传哪些文件？
- 系统是否识别成功？
- 这批数据是否可以进入规整？
- 需要我确认什么？
页面内容：
- 上传区。
- 当前任务进度。
- 文件台账。
- 导入预检查结论。
- 进入规整的主动作。
约束：
- 默认只展示业务结论。
- 技术证据、任务事件和解析细节放到展开区。
- 上传成功不等于导入完成。
- 解析完成不等于数据可用。
- ###3.数据规整
用户问题：
- 字段是否对齐？
- 物资是否匹配？
- 单位是否统一？
- 分类和口径是否一致？
- 哪些记录还不能进入可用数据？
页面内容：
- 字段规整。
- 物资规整。
- 单位与口径。
- 分类与主数据。
- 规整前后对比。
- 低置信和异常入口。
约束：
- 规整操作必须可预演。
- 规则变更必须能看影响范围。
- 低置信结果不得自动进入可用数据。
- ###4.治理待办
用户问题：
- 哪些问题需要我处理？
- 哪些问题影响最大？
- 系统建议怎么处理？
- 我采纳或拒绝后会发生什么？
页面内容：
- 待确认字段。
- 待处理异常。
- 待审核AI建议。
- 规则冲突。
- 重建或发布前阻断项。
约束：
- AI建议不能自动成为事实。
- 批量处理必须展示影响范围。
- 忽略异常不能表达成修复异常。
- 每个处理动作必须留下审计。

### 5. 数据成果
用户问题：
- 现在有哪些规整后的数据？
- 哪些可以导出？
- 哪些仍被阻塞？
- 报表和趋势来自哪些数据版本？
页面内容：
- 规整后数据。
- 可用数据。
- 阻塞数据。
- 汇总报表。
- 趋势分析。
- 导出入口。
约束：
- 数据成果必须展示数据状态。
- 报表应明确数据来源版本。
- 未发布数据不能伪装成正式报告。
- ###6.追溯审计
用户问题：
- 这个结果从哪里来？
- 哪条规则影响了它？
- 谁确认了这个建议？
- 哪次接入或重建产生了这个结果？
页面内容：
- 源文件和Sheet。
- 行级或字段级证据。
- 血缘链路。
- 审计时间线。
- 规则版本和模型建议记录。
约束：
- 追溯能力不能被UI简化删除。
- 审计记录应仅追加。
- 追溯默认从具体结果进入，而不是让用户先理解抽象血缘图。
- ###7.系统设置
用户问题：
- 系统是否正常？
- 本地模型是否可用？
- 数据目录和备份是否正常？
- Token、角色和部署边界是否配置正确？
页面内容：
- API、worker、数据库、前端产物健康状态。
- 模型状态。
- 备份与恢复状态。
- 配置和token
- 运维日志摘要。
约束：
- 普通业务用户默认不进入系统设置。
- 模型细节不应出现在业务主路径。
- 系统健康不能只看API live，应看ready状态。
- ##页面命名建议
建议将现有名称调整为：
- 总览 -> 工作台。
- 接入与任务 -> 数据接入。
- 治理中心 -> 数据规整/治理待办。
- 数据中心 -> 数据成果。
- 问数 -> 问数助手。
- 系统-系统设置。
- 版本血缘、审计时间线 -> 追溯审计。
- ##导航改造原则
- 主导航只放业务用户高频路径。
- 运维、模型和底层证据默认降级。
- 页面名称使用业务语言，不使用内部实现语言。
- 每个页面必须有明确的用户问题。
- 每个页面必须有明确的下一步动作。
- 每个结果必须显示状态：原始、暂存、规整、可用、阻塞、已发布。
