# 09DGX Spark本地模型优化与执行方案
## 文档目的
本文面向smart-material-system在DGX Spark本地设备上的模型执行与运行优化，明确推荐运行形态、资源策略、模型启用顺序、评测门槛和前端表达约束。
本文不替代docs/01-本地模型部署与多模型编排.md、`docs/`09-多模型编排策略.md、`docs/`10-模型评测与验收.md。若本文与正式技术方案冲突，以docs/为准；本文用于把DGX Spark场景下的产品化执行路径和优化优先级讲清楚。
## 一句话结论
DGX Spark适合作为本地部署、内网试运行和业务验收的一体化AI工作站，但不应被设计成“多模型能力展示平台”。
推荐方向是：
"`text
规则优先
 -> 单大模型辅助建议
 -> 低风险任务按需启用fast
 -> 所有模型输出进入校验或人工确认
 -> 通过评测后再扩大常驻模型和并发
## DGX Spark前提
本方案基于以下硬件假设：
DGX Spark / GB10 Grace Blackwell Superchip
128GB统一内存。
本地NVMe存储。
本地模型服务、API、`worker`、前端和数据处理任务运行在同一台设备或同一受控内网环境。
关键判断：
统一内存提高了本地运行大模型的可行性。
统一内存不等于无限资源。
vLLM、FastAPI、`worker`、Excel解析、DuckDB查询和文件写入都会争用同一台机器的CPU、内存、IO和内存带宽。
因此优化重点不是上复杂分布式，而是做好单机资源隔离、任务排队、模型启停和评测门槛。
## 当前方案的主要问题
### 1. 容易把“能跑"误认为“可生产”
DGX Spark可以让本地大模型跑起来，但生产可用还需要证明：
解析大Excel时模型服务是否稳定。
模型生成时API是否仍然可响应。
发布写入时是否会与模型推理争用资源。
重启模型是否影响业务任务。
24小时连续运行是否有00M、端点漂移或任务锁死。
因此，不能因为设备强，就默认启用多模型全常驻和高并发。
### 2. 单机部署不等于单进程耦合
DGX Spark适合单机部署，但不建议把所有能力都放在一个强耦合运行单元中。
开发或演示阶段可以一体化启动；试运行和生产前验收阶段应至少拆成：
pxat...
api
`worker`
writer
model-big
model-fast
embedding
frontend
这些服务可以仍然运行在同一台DGX Spark上，但必须具备独立启动、独立重启、独立日志和健康检查。
### 3. fast+big+embed不应默认全部长期常驻
推荐模型角色是合理的：
big：复杂SQL、低置信修正、质量解释、接入建议。
fast：常规映射、摘要、轻量建议、简单问数。
embed：表头、主数据、指标和few-shot召回。

但三者长期同时常驻必须经过评测证明。
默认不建议：
为了展示能力而同时常驻多个生成模型。
没有评测报告就启用互验。
没有业务收益证明就让fast常驻。
在大文件接入和模型推理之间无限并发。
### 4. 降级策略需要用户可见
模型不可用时，系统可以降级到规则路径或待人工状态。
但不能把降级结果表达为正常结果。
必须明确：
big不可用时，fast只能给候选建议。
fast不可用时，可以转“big，但要记录降级原因。
embed不可用时，可以走词法召回，但要降低置信。
任一模型路径失败，不得静默放行业务事实。
降级结果必须进入待确认或标记为低置信。
### 5. 评测门槛还需要绑定执行开关
`docs/`10-模型评测与验收.md已已经定义了评测方向，但在执行方案上需要明确：
没有评测报告，不启用fast长期常驻。
没有故障注入报告，不启用自动降级扩大使用范围。
没有互验收益证明，不启用互验常态化。
没有复杂SQLA/B结果，不引入Coder模型替换big。
评测不是文档附件，而应该是运行策略开关的依据。
## 推荐运行模式
### 模式A：基线试运行
适用：
初始上线。
业务验收。
数据接入和治理主流程验证。
推荐：
..`text
big：常驻
embed：常驻或词法降级
fast：不常驻
LLM并发：1
max-model-len: 8192
特点：
- 资源稳定。
- 模型职责清楚。
- 易定位问题。
- 适合先把数据接入、规整、人工确认和追溯链路跑通。
约束：
- big只输出建议，不写业务事实。
- 所有低置信建议进入人工确认。
- 大文件解析期间限制模型批处理任务。
### 模式B：轻任务加速
适用：
已有评测集。
fast模型在常规映射、摘要、简单问数中明显降低延迟。
fast人工修正率不高于约定阔值。

推荐：
*"`text
big：常驻
fast：常驻
embed：常驻或词法降级
LLM并发：1-2
使用策略：
- 低风险任务先走fast。
- 校验失败、低置信、schema drift、复杂SQL升级big。
- fast输出不得直接写入业务事实。
启用门槛：
-p95延迟明确下降。
-人工修正率不升高。
-24小时无00M、无频繁端点重启、无任务锁死。
### 模式C：评测或专项能力模式
适用：
-Coder模型A/B。
-独立互验实验。
-SQL复杂能力专项评测。
推荐：
""`text
big/coder：二选一或按窗口切换
fast：视评测需要启用
embed：可启用
互验：只用于评测，不默认生产常态化
约束：
- 三生成模型长期同时常驻。
- 不建议fast+big+coder
- 互验失败必须进入unverified或conflict”。
- 互验不能用fallback结果冒充独立模型一致。
## 资源优化策略
### 1. 并发策略
初始建议：
LLM生成并发从1起步。
-大文件解析并发从1起步。
文件导入、质量预检、发布写入、模型建议应进入统一任务队列。
大批量Excel解析时暂停或降低后台LLM批处理。
原因：
DGX Spark是强单机，但文件解析、DuckDB、vLLM共享CPU、内存、IO和内存带宽。并发过高会导致全系统抖动，而不是单个模型慢。
### 2. 上下文长度策略
默认建议：
"`text
max-model-len = 8192
不建议默认使用超长上下文。
原因：
本系统主要处理结构化字段、样例值、质量摘要和SQL口径。
-不需要把整本Excel或大段原始数据塞给模型。
超长上下文会占用显著KVcache，降低稳定性和吞吐。

### 3. 输入裁剪策略
模型输入必须是裁剪后的证据包：
字段名。
Sheet角色。
少量样例值。
质量摘要。
候选规则。
输出schemao
校验错误。
模型不应直接读取：
完整源文件。
数据库。
任意SQL执行能力。
原始文件目录。
Shel1或任意网络。
### 4. Embedding策略
优先顺序：
""`text
规则字典
 -> 历史人工确认映射
 -> embedding召回
 -> 词法召回fallback
 -> 生成模型建议
 -> 人工确认
约束：
embedding只做候选召回。
embedding结果不能直接写事实。
embed服务不可用时，词法召回可以兜底，但应降低置信度。
### 5. 模型启停策略
建议：
- big作为核心生成模型，优先保障稳定。
- fast”不应在未评测前默认常驻。
- coder不应与“big长期同时常驻，除非评测证明收益明确。
模型重启应通过运维动作触发，并记录审计。
模型端点健康检查应进入系统状态页，而不是业务用户主路径。
## 执行步骤
### 第一步：冻结Stage1基线
目标：
明确当前系统是规则优先、模型辅助建议。
不宣称自动治理。
不宣称完整生产级多模型编排。
执行：
- 1.确认“big端点可用。
- 2.确认embed可可用或启用词法fallback。
- 3.将fast作为可选，不作为生产默认依赖。
- 4.前端文案统一为“AI建议""本地模型状态”，避免“自动处理”
验收：
模型不可用时，接入、规整、质量预检仍能走规则路径。
模型输出不会直接写业务事实。
页面能说明模型不可用的影响范围。

### 第二步：单机服务拆分
目标：
在DGX Spark单机内形成清晰运行边界。
推荐服务：
""`text
api：接口、鉴权、任务入队、状态查询
`worker`：接入、画像、质量预检、模型建议任务
writer：业务事实写入、发布、审计
model-big：大模型服务
model-fast：小模型服务，可选
embedding：向量召回服务，可选
frontend：前端静态资源
执行：
- 1.开发环境可以保留一体化脚本。
- 2.试运行环境使用Compose或等价进程管理。
- 3.每个服务独立日志。
- 4.每个服务独立健康检查。
- 5.模型服务重启不应导致API直接不可用。
验收：
model-big后，API能正常返回模型不可用状态。
停止
停止worker后，API仍能查看历史数据和任务状态。
停止API后，已发布数据不丢失。
### 第三步：统一模型路由
目标：
所有模型调用都经过统一策略，不让业务模块自行决定模型角色。
执行：
- 1.将任务类型集中到“TaskPolicy
- 2.每个任务定义primary、escalate、risk、max_calls、timeout。
- 3.所有模型调用统一走*PolicyRouter
- 4.模型输出必须经过schema或业务规则校验。
- 5.降级结果必须带"degraded"、*needs_confirm或等价状态。
验收：
代码中没有散落的直接chat（role="big"）决策。
高风险任务不能因为fallback而变成高置信。
模型调用审计能看到task_type、role、`endpoint`、model、状态和错误。
### 第四步：评测绑定启用
目标：
让模型启用策略由评测报告驱动。
执行：
- 1.建立data/eval/评测样本。
- 2.覆盖字段映射、主数据匹配、质量解释、简单SQL、复杂SQL、故障注入。
- 3.记录每次评测的模型revision、SHA、镜像版本、延迟、修正率、失败率、内存峰值。
- 4.评测通过后再启用fast常驻或互验。
验收：
没有评测报告，不开启fast生产常驻。
没有互验收益报告，不开启互验常态化。
评测失败时，系统退回基线模式。

### 第五步：前端表达收敛
目标：
普通用户看到的是业务状态，不是模型部署细节。
执行：
- 1.普通业务路径只显示AI建议"建议待确认”
- 2.模型endpoint、模型id、token、rawresponse 放到系统设置或运维详情。
- 3.降级建议必须标明“需要人工确认”。
- 4.问数结果必须标明数据状态：可用数据、发布数据或暂存数据。
验收：
用户不会误以为模型已经自动治理数据。
用户能区分规则判断、模型建议、人工确认和发布结果。
模型状态不打断数据规整主流程。

## 监控与验收清单
上线前至少确认：
- 模型端点健康状态可见。
模型调用失败可见。
circuit open 状态可见。
降级原因可见。
LLM调用有审计记录。
模型不可用不会阻塞规则路径。
大文件解析和模型建议不会无限并发。
发布写入不依赖模型即时可用。
24小时试运行无00M、任务锁死、端点频繁重启。
fast常驻、互验、Coder替换均有评测报告支撑。
## 不建议做的优化
### 不建议1：过早追求多模型常驻
多模型常驻会增加内存压力、启动复杂度和故障定位难度。没有评测收益前，不应作为默认方案。

### 不建议2：把模型能力放到用户主路径
用户主路径是数据规整，不是模型管理。模型能力应隐藏在建议、解释和问数辅助后面。
### 不建议3：用模型替代规则和人工确认
字段、物资、单位、库存事实、正式发布都必须由规则、校验和人工确认闭环，不能由模型直接决定。
### 不建议4：默认超长上下文
超长上下文会显著增加资源占用。本系统应优先使用结构化摘要和证据包，而不是把原始文件全文交给模型。
## 不建议5:把DGX Spark当成集群
DGX Spark是强本地工作站。优化方向应是单机可靠运行、资源调度和可恢复性，而不是一开始引入复杂分布式架构。
## 最终推荐路线
text
阶段1：规则优先+big辅助建议+embed/词法召回
阶段2：基于评测启用fast承接低风险任务
阶段3：统一PolicyRouter、审计、降级和任务预算
阶段4：按评测决定是否保留互验或Coder模型
阶段5：形成可复制部署和运维验收清单
DGX Spark的价值在于让系统可以本地化、自主可控地完成智能数据规整。系统设计应优先保障数据可信、运行稳定和人工确认链路，而不是追求模型数量和自动化表述。
